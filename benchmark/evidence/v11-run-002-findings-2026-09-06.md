## 1. Execution succeeded. That is a separate claim from the answers being valid.

The harness executed every unit it planned. 308 units, 308 terminal records, no
crash, no lost unit, ~2h55m. `status: "COMPLETE"` is correct and stays as it is:
it means every planned unit reached a terminal record, which is true.

What it does not mean is that 204 units produced a usable measurement. They did
not. Sorting the same records by *what they answered* rather than by *whether
they ran* gives a different run:

| | harness recorded | corrected |
|---|---|---|
| MEASURED | 204 | **156** |
| FAILED | 84 | **132** |
| EXCLUDED | 20 | 20 |

The 48-unit difference is not a judgement call. `preregistration.json:280`
defines `falseAlertRate` and then says, in the frozen text:

> Null, malformed, or missing is a failed unit, not a negative prediction.

48 `D_FALSE` units answered `changedFactDetected: null` and were recorded
MEASURED. Under the sentence above they are failed units. The harness and the
frozen text disagreed, and the frozen text governs.

Two things that look like the same reclassification are **not**, and are left
alone:

- `changedFactDetection` for `D_TRUE` reads "1 only when ... ; **otherwise 0**".
  A null there scores 0. It is a wrong answer, not a failed unit.
- `decisionRetrievalAccuracy` for Phase B reads "1 only when ... ; **otherwise
  0**". Same.

An earlier draft of this analysis classified those as "unscorable". That
over-reached, and the class is withdrawn. No new unit status was invented: the
four in `v11-contract.mjs` (`MEASURED`, `FAILED`, `NOT_MEASURED`, `EXCLUDED`)
are the only ones used, and failure causes come from the existing closed
`ADAPTER_FAILURE_CAUSES` enum.

## 2. The headline finding: the harness penalises exactly the arms that retrieve

Look again at the `D_FALSE` columns. Every memory arm that answered failed all
three probes. The control passed all three. That pattern is not a product
result — it is the harness measuring itself.

**The mechanism.** `v11-contract.mjs:207`, `standardizedDecisionRecord`, stores
each decision response as the memory record's content verbatim
(`content: structuredClone(decisionResponse)`). The adapters return record
content verbatim as native context. So a memory arm's phase-D prompt carries
several already-filled copies of the exact object the model is being asked to
produce — and under `canonicalJson` key order, each copy begins
`"changedFactDetected":null`. The 7B model transcribes the value it was shown.

**The evidence, three independent ways:**

1. **Perfect correlation with retrieved context.** 48 of 48 `D_FALSE` nulls
   occur in arms with `nativeContextCount` of 4–6. 0 of 12 occur in the control,
   whose `nativeContextCount` is 0. No exceptions in either direction.
2. **Field-level copying.** Comparing each arm's `D_TRUE` answer to its own
   phase C answer: every memory arm is identical on 14 of 15 fields (only
   `changedFactId` differs). The control is identical on 2 of 15.
3. **A controlled experiment.** Flipping only that one field inside the
   retrieved records, at an identical 1278 `prompt_tokens`, flipped the model's
   answer to `true`.

**Failure layer: the harness's own prompt and record format, plus 7B model
capacity. Not a ShadowGraph product failure, and not a competitor product
failure.** This single defect accounts for all 48 `D_FALSE` rule-failures and
all 16 `D_TRUE` zeros, and it does so only in arms that retrieve. The
measurement is confounded systematically **in the control's favour**.

## 4. Fixes landed

### F30 — the scorer (`scoring.mjs`, `aggregate.mjs`)

Three defects, one shape: an absent answer scored as a good one.

- `falseAlertRate` divided by however many probes it found and counted a null as
  a negative. An arm answering none of the three posted the best false-alert
  rate in the run. Now: the rate exists only when all three probes carry a real
  boolean, otherwise **N/A (`null`), never 0**; and
  `falseAlertProbesRequired/Valid/Failed` travel beside it so a null rate can be
  told apart from a set that never ran.
- `projectIsolation`/`userIsolation` returned **1 — the best score, on a hard
  security gate** — for a probe that returned nothing. The frozen rule says "1
  **only when** <response clean> **and** <persisted-state inspection confirms>".
  Now: 1 requires both halves; a leak is 0; an absent answer or absent
  inspection is N/A.
- The persisted-state half was never consulted at all — it read `leakedRecordIds`
  and `persistedLeak`, neither of which any adapter writes, so it answered "no
  leak" for every unit ever scored. Now it reads the evidence the adapters do
  record (`verified` plus `matchingRecordIdCount`/`matchingContentCount`), and a
  match count overrules an adapter's own `verified` claim.

Arms declaring `persistence: NOT_APPLICABLE` (the control) are not asked for an
inspection. The v1.0 lifecycle's `persistedLeak` boolean is honoured as the
inspection outcome it stands for, so **frozen v1.0 scores are unchanged**; its
identical weakness is recorded rather than fixed as a side effect of a v1.1
repair.

### F29 — Basic Memory storage (`basic_memory_adapter.py`)

The adapter reported MEASURED bytes by walking the project directory, on the
stated premise that "the arm's records are the files in it". Basic Memory 0.23.2
writes note bodies to `note_content.markdown_content` in a SQLite index shared
by every project, and queues the markdown write for
`drain_pending_materializations()`, whose callers are lifespans the adapter
never enters. So the records exist and the directory stays empty, and the arm
published **MEASURED 0 bytes for namespaces that were holding records** — the
most favourable number available, under the status that means it is exact. The
fail-closed guard could not fire because `_project_path` creates the directory
before anything asks whether it exists.

The arm now declares `NOT_AVAILABLE`, as mem0 and cognee do. **LB2c's clearance
is withdrawn** in `CANDIDATE-STATUS.md` rather than quietly amended.

One of the three replaced tests wrote the missing files into the directory by
hand and explained that it had to, because "the fake client keeps its notes in a
dictionary, so the project directory is empty". That empty directory was the
product's real behaviour; supplying the missing files turned the defect into the
fixture.

### Reporting (`aggregate.mjs`)

`coverage` now reports planned/MEASURED/FAILED/NOT_MEASURED/EXCLUDED for the
run, per arm, and per phase, plus a tally of recorded failure causes, with
totals that reconcile with the unit count in every breakdown.

## 6. Is the MCP mode distinction actually exercised?

Yes — and its savings are still not measurable here.

The mode is wired end to end: `v11-node-hosts.mjs:33-34` maps each arm to its
mode, `mcpHost` refuses a descriptor whose mode contradicts its arm,
`shadowgraph.mjs:344` translates it to `compact: mode === 'compact'`, the child
gets `SHADOWGRAPH_MCP_COMPACT`, and the handshake asserts the tool list — 21
tools for Full, 12 for Compact. The two arms genuinely ran different surfaces.

But the schema overhead never reaches anything the benchmark meters. Over 40
measured units each, the arms differ by 49 prompt tokens in total (47,858 vs
47,809, about 0.1%) and by 0 MCP tool calls (156 each). The outer decision model
is given scenario text and native context — never the MCP tool schemas — so the
tool-list difference lives entirely inside the adapter's handshake, which is not
a metered request class.

**So Compact's savings are real in the product and structurally invisible to
this benchmark**, for the same reason as `decisionRetrievalAccuracy`: the
metric's input never reaches the measured surface. Any Compact efficiency claim
needs a different instrument, not this run.

## 8. Recommendation

**VALID FOR DIAGNOSTICS ONLY.**

- **Valid as diagnostics.** The run is the first end-to-end execution of the
  v1.1 harness, it completed every planned unit, its artifacts are preserved and
  checksummed, and it found four real defects that five rounds of adversarial
  review did not — because they only appear when something actually runs.
- **Not valid as a comparative result.** The D-phase metric is confounded by the
  harness's own record format for every arm that retrieves (F32);
  `decisionRetrievalAccuracy` measures nothing for any arm (F31); the scorer
  that produced the numbers had the defects fixed in F30; and no arm is
  rank-eligible under `winTieRules.eligibility` regardless of any of that.
- **Not invalid.** Nothing about the execution was unsound. The unit records are
  faithful accounts of what happened. It is the interpretation of `null` answers
  as product behaviour that does not hold.

**No scored run, no publication, no version bump, and no comparative claim
follows from this run.** F31 and F32 must be closed first, and F31 needs an
amendment, not a code change.
