## 1. Execution succeeded. That is a separate claim from the answers being valid.

The harness executed every unit it planned. 308 units, 308 terminal records, no
crash, no lost unit, 2h52m. `status: "COMPLETE"` is correct and stays as it is:
it means every planned unit reached a terminal record, which is true.

What it does not mean is that 204 units produced a usable measurement. They did
not. Sorting the same records by *what they answered* rather than by *whether
they ran* gives a different run:

| | harness recorded | corrected |
|---|---|---|
| MEASURED | 204 | **156** |
| FAILED | 84 | **132** |
| EXCLUDED | 20 | 20 |

The corrected column is computed by hand in this report. **No artifact produces
it**: the new `aggregate.coverage` block counts `unit.status`, so run over the
preserved raw it still reports `MEASURED: 204, FAILED: 84`. That gap is
deliberate and is recorded as **F36** — see section 5 for why the runner's
status assignment was left alone, and why the gap is still a defect.

The 48-unit difference is not a judgement call. `preregistration.json:280`
defines `falseAlertRate` and then says, in the frozen text:

> Null, malformed, or missing is a failed unit, not a negative prediction.

48 `D_FALSE` units answered `changedFactDetected: null` and were recorded
MEASURED. Under the sentence above they are failed units. The harness and the
frozen text disagreed, and the frozen text governs.

Two things that look like the same reclassification are **not**, and are left
alone:

- `changedFactDetection` for `D_TRUE` reads "1 only when ... ; **otherwise 0**".
  A null there scores 0. It is a wrong answer, not a failed unit.
- `decisionRetrievalAccuracy` for Phase B reads "1 only when ... ; **otherwise
  0**". Same.

An earlier draft of this analysis classified those as "unscorable". That
over-reached, and the class is withdrawn. No new unit status was invented: the
four in `v11-contract.mjs` (`MEASURED`, `FAILED`, `NOT_MEASURED`, `EXCLUDED`)
are the only ones used, and failure causes come from the existing closed
`ADAPTER_FAILURE_CAUSES` enum.

## 2. The headline finding: the harness corrupts the D phase for every arm that retrieves

Look again at the `D_FALSE` columns. Every memory arm that answered returned
`null` to all three probes and is therefore a failed unit under the frozen rule.
The control returned a real boolean to all twelve — and every one of them was
`true`, which on a `D_FALSE` probe is a **false alert. The control's false-alert
rate is 12/12, the worst possible.** Its units are valid; its answers are as
wrong as answers get.

That distinction matters, and an earlier draft of this section got it wrong by
writing that "the control passed all three". It did not pass. It answered.

**The mechanism.** `v11-contract.mjs:225`, `standardizedDecisionRecord`, stores
each decision response as the memory record's content verbatim
(`content: structuredClone(decisionResponse)`). The adapters return record
content verbatim as native context. So a memory arm's phase-D prompt carries
several already-filled copies of the exact object the model is being asked to
produce — and under `canonicalJson` key order, each copy begins
`"changedFactDetected":null`. The 7B model transcribes the value it was shown.

**The evidence, three independent ways:**

1. **Perfect correlation with retrieved context.** 48 of 48 `D_FALSE` nulls
   occur in arms with `nativeContextCount` of 4–6. 0 of 12 occur in the control,
   whose `nativeContextCount` is 0. No exceptions in either direction.
2. **Field-level copying.** Comparing each arm's `D_TRUE` answer to its own
   phase C answer: every memory arm is identical on 14 of 15 fields (only
   `changedFactId` differs). The control is identical on 2 of 15.
3. **A controlled experiment.** Flipping only that one field inside the
   retrieved records, at an identical 1278 `prompt_tokens`, flipped the model's
   answer to `true`. (1278 is verifiable as the real `prompt_tokens` of
   `shadowgraph-full / D_TRUE / ACC_INCIDENT_HANDOFF / r0` in the preserved raw.
   **The experiment's own transcript was not preserved**, so this third strand
   rests on a run that cannot now be re-inspected. The first two strands are
   reproducible from the preserved artifact alone and are sufficient on their
   own.)

**Failure layer: the harness's own prompt and record format, plus 7B model
capacity. Not a ShadowGraph product failure, and not a competitor product
failure.**

**This is now fixed (F32).** `serializeNativeContext` drops `changedFactDetected`,
`changedFactId` and the prior `decisionId` echo from a decision record before
rendering it into the prompt, so the model is no longer shown its own previous
answer to the question being asked. `record.id` survives, the stored record keeps
all fifteen frozen fields and still satisfies the adapter protocol's exact-keys
validator on both the JS and the Python side, and **both prompt-binding hashes
were recomputed after the fix and still match the values run 002 recorded**. Run
002 is not re-scored; the fix governs the next run, which will be a new run id.

This single defect accounts for all 48 `D_FALSE` rule-failures and for 16 of the
18 `D_TRUE` zeros. **It does not account for all of them.** The remaining two are
the control's, on `ACC_INCIDENT_HANDOFF`, where it answered
`changedFactDetected: true` with `changedFactId: "unresolvedCaseCount"` — the
review trigger's key rather than the fixture id `handoff-backlog-rise`. So the
control failed half its `D_TRUE` units too, for an unrelated reason, and any
framing of the form "only the arms that retrieve got this wrong" is not clean.
An earlier draft said 16 zeros and "only in arms that retrieve"; both were wrong,
and the correction weakens the asymmetry rather than the mechanism.

**On which direction the confound runs: it depends on the metric, and an earlier
draft stated it too flatly as "in the control's favour".** Under the scorer that
actually produced run 002's numbers, `falseAlertRate` came out **0.0 for the
memory arms and 1.0 for the control** — the confound flattered the memory arms
there, because a null read as a correct negative. On `changedFactDetection` it
ran the other way: 0 of 4 for each memory arm against 2 of 4 for the control.
After F30 the memory arms get N/A rather than a flattering 0.0. What is true in
both directions, and is the point, is that **none of those numbers measures a
memory product**.

## 4. Fixes landed

### F30 — the scorer (`scoring.mjs`, `aggregate.mjs`)

Three defects, one shape: an absent answer scored as a good one.

- `falseAlertRate` divided by however many probes it found and counted a null as
  a negative. An arm answering none of the three posted the best false-alert
  rate in the run. Now: the rate exists only when all three probes carry a real
  boolean, otherwise **N/A (`null`), never 0**; and
  `falseAlertProbesRequired/Valid/Failed` travel beside it so a null rate can be
  told apart from a set that never ran.
- `projectIsolation`/`userIsolation` returned **1 — the best score, on a hard
  security gate** — for a probe that returned nothing. The frozen rule says "1
  **only when** <response clean> **and** <persisted-state inspection confirms>".
  Now: 1 requires both halves; a leak is 0; an absent answer or absent
  inspection is N/A.
- The persisted-state half was never consulted at all — it read `leakedRecordIds`
  and `persistedLeak`, neither of which any adapter writes, so it answered "no
  leak" for every unit ever scored. Now it reads the evidence the adapters do
  record (`verified` plus `matchingRecordIdCount`/`matchingContentCount`), and a
  match count overrules an adapter's own `verified` claim.

Arms declaring `persistence: NOT_APPLICABLE` (the control) are not asked for an
inspection.

**What this does to v1.0**, stated precisely, because an earlier draft said
"frozen v1.0 scores are unchanged" and that is not true as written:

- **Isolation scores are unchanged.** `validate.mjs:503` requires a MEASURED
  v1.0 unit to carry a response object and `summarizeArm` requires every phase
  MEASURED, so the new null branches are unreachable there; `persistedLeak` is
  always a boolean out of the v1.0 `lifecycleFrom`, so `inspection` is never
  null. Verified old-against-new over five v1.0-shaped lifecycles.
- **`falseAlertRate` does change for v1.0.** The v1.0 response schema permits
  `changedFactDetected: null` (`preregistration.json:50`) and the legacy
  validator never checks it, so a schema-legal null used to score 0 and now
  scores N/A. That is deliberate: `preregistration.json:280` is **v1.0's own
  frozen rule**, and the old code violated it on the v1.0 path too. No published
  v1.0 result moves, because `benchmark/results/` holds no v1.0 raw run.
- The three added metric fields cannot change any score: `METRIC_NAMES` does not
  include them and `efficacyComposite` does not read them.

The v1.0 `persistedLeak` boolean is honoured as the inspection outcome it stands
for. It is worth being blunt about what that means: because nothing writes
`persistedLeak`, it is always `false`, so every v1.0 isolation unit with a clean
response scores 1 from an inspection that never happened. That is **F35**, left
open deliberately — closing it would restate frozen v1.0 results as a side
effect of a v1.1 repair.

### Two further fail-opens, found by the independent closure review of these fixes

- **`null <= 0.05` is `true` in JavaScript.** Making the rate N/A closed one
  fail-open and opened another a layer up: `bestCandidate` and `pairwiseWin`
  compared the rate directly, so an arm with an *undefined* false-alert rate
  would have passed the marketing threshold and won a pairwise comparison on a
  number it does not have. Before the F30 fix a null rate was nearly
  unreachable; afterwards it is the correct answer whenever a probe failed.
  Both gates now require a finite rate **and** a finite limit.
- **`isolationInspectionFrom` let `verified` stand alone.** With
  `Number(undefined) || 0`, an evidence object carrying `verified: true` and no
  match counters read as a confirming clean inspection — the opposite of the
  function's own contract that the counts win. Missing counters now mean "not an
  inspection" (N/A). Relatedly, an inspection that ran and confirmed nothing is
  now N/A rather than 0: charging the arm a zero bills it for a defect in the
  inspection.

### F29 — Basic Memory storage (`basic_memory_adapter.py`)

The adapter reported MEASURED bytes by walking the project directory, on the
stated premise that "the arm's records are the files in it". Basic Memory 0.23.2
writes note bodies to `note_content.markdown_content` in a SQLite index shared
by every project, and queues the markdown write for
`drain_pending_materializations()`, whose callers are lifespans the adapter
never enters. So the records exist and the directory stays empty, and the arm
published **MEASURED 0 bytes for namespaces that were holding records** — the
most favourable number available, under the status that means it is exact. The
fail-closed guard could not fire because `_project_path` creates the directory
before anything asks whether it exists.

The arm now declares `NOT_AVAILABLE`, as mem0 and cognee do. **LB2c's clearance
is withdrawn** in `CANDIDATE-STATUS.md` rather than quietly amended.

One of the three replaced tests wrote the missing files into the directory by
hand and explained that it had to, because "the fake client keeps its notes in a
dictionary, so the project directory is empty". That empty directory was the
product's real behaviour; supplying the missing files turned the defect into the
fixture.

### Reporting (`aggregate.mjs`)

`coverage` now reports planned/MEASURED/FAILED/NOT_MEASURED/EXCLUDED for the
run, per arm, and per phase, plus a tally of recorded failure causes, with
totals that reconcile with the unit count in every breakdown.

## 6. Is the MCP mode distinction actually exercised?

Yes — and its savings are still not measurable here.

The mode is wired end to end: `v11-node-hosts.mjs:33-34` maps each arm to its
mode, `mcpHost` refuses a descriptor whose mode contradicts its arm,
`shadowgraph.mjs:344` translates it to `compact: mode === 'compact'`, the child
gets `SHADOWGRAPH_MCP_COMPACT`, and the handshake asserts the tool list —
**27 tools for Full, 12 for Compact** (`node-adapter-host.mjs:25-53` and
`55-68`; an earlier draft said 21 for Full, which was a miscount). The two arms
genuinely ran different surfaces.

But the schema overhead never reaches anything the benchmark meters. Over 40
measured units each, the arms differ by 49 prompt tokens in total (47,858 vs
47,809, about 0.1%) and by 0 MCP tool calls (156 each). The outer decision model
is given scenario text and native context — never the MCP tool schemas — so the
tool-list difference lives entirely inside the adapter's handshake, which is not
a metered request class.

**So Compact's savings are real in the product and structurally invisible to
this benchmark**, for the same reason as `decisionRetrievalAccuracy`: the
metric's input never reaches the measured surface. Any Compact efficiency claim
needs a different instrument, not this run.
