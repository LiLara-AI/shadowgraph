## ADR-0001 — Simple append-oriented journal with projections; NOT full event sourcing

- **Status:** `accepted` (2026-08-25) — implemented in `src/journal.js` + `appendJournal()`. **X-3 equivalence gate PASSED**: canonical projection equivalence verified on JSON and SQLite after repeated restarts (test `R3`). **X-2 settled by measurement**: rebuild p95 4.77 ms at 10k entries vs a 250 ms threshold, journal/projection ratio 3.4× vs a 10× threshold, so snapshots stay deferred by measurement (`docs/benchmark-report.md`). Sub-decisions resolved: **J-1** baseline accepted as an honestly-labelled reconstruction; **J-2** `decision.aged`/`fact.expired` ARE journalled because they mutate stored state; **J-3** `reviewSignals` stay out of the journal and are regenerated by `review()`.
- **Date:** 2026-08-25
- **Supersedes on acceptance:** the wholesale-ledger framing in `docs/shadowgraph-redesign-proposal.md`
- **Directive basis:** user directives 2 and 3 (2026-08-25)

### Context

The redesign proposal specifies a canonical event ledger with rebuildable projections as the foundation for everything. Two verified facts constrain this:

1. **No ledger exists today.** Events carry only `{id, type, at, project, recordId}` — no payload. Rebuilding from `{events}` alone yields **0 decisions** (gap G4, proven — `test-and-benchmark-log.md` T6/P4). This is greenfield construction.
2. **A working system passes 41 tests** with zero dependencies and zero audit vulnerabilities (verified T2/T4).

✅ **PRIMARY-SPEC** — Microsoft Azure Architecture Center (source S10, accessed 2026-08-25), verbatim:

> *"Event sourcing is a complex pattern that introduces significant trade-offs… **It's costly to migrate to or from** an event sourcing solution, and after you adopt the pattern, **it constrains future design decisions**… **For most systems and most parts of a system, traditional data management is sufficient.**"*
>
> *"Event sourcing doesn't have to be an all-or-nothing decision… **Apply it selectively**… Use traditional CRUD for parts when the complexity isn't justified."*

### Decision

**Do not implement full event sourcing.** The official recommendation is a **simple append-oriented journal (transactional history)** with **projections and snapshots only where a specific requirement or measurement demands them**.

Concretely:

1. **Journal scope — audit-critical claims only:** decisions, alternatives, facts, attempts, outcomes, confidence changes. Each journal entry carries a **complete payload** plus provenance, actor/client/session, timestamp, and schema version.
2. **Not journalled** (ordinary mutable state): review signals, idempotency records, project summaries, validation results. These are derived or operational, not claims about the world.
3. **Existing entity maps remain the read path.** Projections are built *from* the journal and compared against current output for equivalence. Projections replace the read path only after equivalence is proven on fixtures.
4. **Snapshots are deferred** until a measurement shows rebuild is too slow (assumption X-2). Do not build snapshotting speculatively.
5. **CQRS is not adopted.** No command/query separation, no eventual consistency, no separate read stores.
6. **Schema evolution** uses the three strategies Microsoft documents: tolerant deserialization, explicit event versioning, and upcasting.
7. **Dual-write behind a feature flag** (`SHADOWGRAPH_LEDGER=1`), default off. Nothing working is deleted in this phase.

**Terminology discipline (user directive 2):** the journal is described as **"append-oriented with documented deletion semantics"** — **never** as "append-only", because hard purge removes entries. Any doc claiming append-only must be corrected.

### Purge semantics — decided

Adopted per user directive 2:

| Operation | Behaviour | Default? |
| --- | --- | --- |
| **`purgeProject` (logical / tombstone)** | Writes an auditable `project.purged` journal entry; removes record payloads; **retains journal skeleton** (entry ids, types, timestamps, project) so the history remains auditable and projections remain rebuildable. | ✅ **Yes** |
| **Hard purge (separate, explicit)** | Physically removes the requested data from storage, **including journal entries**. Irreversible. Never invoked implicitly, never by default, and never as a fallback from logical purge. | ❌ No — explicit opt-in only |

Documentation requirements:
- Hard purge is documented as **an exception serving the right to erasure**, and as genuinely removing the requested data from storage.
- Documentation must state plainly that **after a hard purge the journal is no longer append-only**, and must describe the deletion semantics.
- Logical purge must not be described as "deletion" without qualification, since payload removal retains a skeleton.

Test requirements (user directive 2 — independent tests for each):
1. Tombstone purge: payloads gone, journal skeleton retained, `project.purged` entry written, other projects unaffected.
2. Hard purge: requested data physically absent from storage, including journal entries.
3. **Rebuild after tombstone purge** succeeds and omits purged payloads.
4. **Rebuild after hard purge** succeeds and is internally consistent (no dangling references).
5. Hard purge is never reachable from the default code path.

### Options considered

| Option | Verdict |
| --- | --- |
| **A. Simple append-oriented journal, audit-critical scope, projections on demand, snapshots deferred, no CQRS** | ✅ **Chosen** |
| B. Full event sourcing + CQRS for all state, as the redesign proposal specifies | ❌ Rejected |
| C. Keep the current metadata-only event trail; just add payloads | ❌ Rejected |
| D. No structural change; fix only the principle violations | ❌ Rejected as an endpoint (but is the correct first increment — ADR-0002) |

**Why B rejected:** contradicts S10 on three counts — costly to migrate *from*, constrains future design, unjustified for most parts of a system. Applying ES to idempotency keys and review-signal status is the boilerplate ⚠️ Dudycz (S11) warns of for dictionary-like data. It also maximises blast radius against a working 41-test system for no user-visible benefit on non-audit paths. **User directive 3 forecloses it.**

**Why C rejected:** `purgeProject` currently splices the event array (G5, proven: events `1` → `0`), so the collection is not append-oriented in any enforced sense. Adding payloads to a freely-mutated array produces something that *looks* like a journal and is not one — worse than none, because it invites reliance on a guarantee that does not hold.

**Why D rejected as an endpoint:** G1 cannot be fixed *durably* without somewhere to record fact-observation and reconsideration entries with provenance.

### Consequences

**Positive:** bounded blast radius; the audit trail the product promises becomes real; no new dependencies; complexity stays proportional to the actual requirement; snapshots/CQRS are not paid for until needed.

**Negative:** two storage concepts coexist during migration (journal + maps) — genuine added complexity, must be documented; the flag is temporary maintenance burden; equivalence testing is required on every write path.

**Assumptions to validate, not assume:** X-2 (rebuild fast enough without snapshots), X-3 (projection output can be made equivalent), X-4 (SQLite full-rewrite-per-save acceptable). See "Unresolved assumptions" in `current-status.md`.

### G4 DETAILED DESIGN (historical snapshot; status `proposed` at time of writing)

Answers the 14 design questions required before implementation. **Nothing below is implemented.**

#### D1 — Journal scope: what writes an entry

| Operation | Entry type | Notes |
| --- | --- | --- |
| `addDecision` | `decision.recorded` | includes its alternatives — see D2 |
| `addFact` | `fact.observed` | |
| `addFact` superseding a prior fact | `fact.superseded` | the *implicit* supersession at `addFact` line ~88 is currently silent; it becomes explicit |
| `addAttempt` | `attempt.recorded` | |
| `setOutcome` | `outcome.recorded` | |
| `setOutcome` confidence side-effect | `confidence.changed` | **separate entry** — the confidence move is a distinct claim from the outcome |
| `updateDecisionStatus` | `decision.status_changed` | carries `from` and `to` |
| `supersedeDecision` | `decision.superseded` | |
| `link` | `relation.created` | |
| `maintain` aging a decision | `decision.aged` | derived, but it mutates stored state, so it is journalled |
| `maintain` expiring a fact | `fact.expired` | |
| `purgeProject` (tombstone) | `project.purged` | see D11 |

**Alternatives do NOT get their own entries.** They have no independent mutation API — they are only created inside `addDecision` and read by `review()`. Giving them entries would imply an editing capability that does not exist. They ride inside the decision snapshot.

#### D2 — What stays mutable, outside the journal

`reviewSignals` (derived by `review()` from decisions+facts; rebuildable by re-running `review()`), `idempotency` (an execution-control cache — but see D7), `revision` (storage concurrency token, not a domain claim), and everything `validate()`/`repairPlan()`/`stats()` compute on the fly.

Rationale: these are projections or plumbing. Journalling them is the "enormous boilerplate for dictionary data" that Dudycz warns about (S11) and Microsoft's *"use traditional CRUD for parts when the complexity isn't justified"* (S10).

#### D3 — Journal entry schema

```jsonc
{
  "id": "jentry_<ts>_<rand>",     // entry identity
  "seq": 1,                        // REQUIRED monotonic integer — the ordering key (D5)
  "type": "fact.observed",
  "at": "2026-08-25T10:00:00.000Z",// human/temporal only, NOT the sort key
  "project": "default",
  "entityId": "fact_...",          // renamed from recordId/factId; one field, not two
  "entityKind": "fact",            // decision | attempt | fact | relation | project
  "schemaVersion": 3,              // per-entry, enables upcasting (D10)
  "payload": { /* see D4 */ },
  "provenance": {                  // the ACTOR OF THE WRITE, not the claim's origin
    "actor": null, "client": null, "sessionId": null
  },
  "idempotencyKey": null,          // present when the operation carried one (D7)
  "causationId": null              // seq or id of the entry that caused this one
}
```

`causationId` **is** required, for exactly one reason: `setOutcome` emits two entries (`outcome.recorded` + `confidence.changed`) and `maintain` can emit many. Without causation, a reader cannot tell that a confidence move was caused by a specific outcome rather than asserted independently. It is `null` for user-initiated entries.

**Naming note:** today's events use `recordId` for decisions/attempts and `factId` for facts. The journal unifies on `entityId` + `entityKind`. Old events are not rewritten (D9).

#### D4 — Payload representation: **complete post-operation snapshot of the affected entity**

Chosen over the two alternatives:

| Option | Rejected because |
| --- | --- |
| **Command/operation** (store the caller's input, rebuild by re-executing) | Rebuild output would depend on the *code version doing the replay*. `id()` and `now()` are non-deterministic, so replay could not reproduce ids or timestamps. Worse, replaying an `addFact` command through future code could produce a *different* verification outcome — reopening the G2 bypass by the back door. Disqualifying. |
| **State delta** | Compact, but an entry is unreadable alone, rebuild requires a correct base plus every intervening delta, and a single corrupt delta poisons everything after it. |
| **✅ Complete post-op snapshot** | Deterministic (rebuild is a fold, not a re-execution), self-describing (one entry fully explains one state), version-independent, and a corrupt entry damages one entity rather than the chain. |

Rebuild becomes: **fold entries in `seq` order; for each, set `entity[entityId] = payload`.** Last writer per entity wins. No domain logic runs, so no validation can be bypassed and no clock is consulted.

**Cost, stated honestly:** storage grows with `entity size × mutation count` rather than with change size. A decision is roughly 1–3 KB and realistically mutates 5–20 times, so a 1,000-decision project lands in the low tens of MB. Acceptable for local-first single-user. Mitigation if X-2 fails is compaction (drop superseded snapshots older than the last N per entity) — **not** built now.

**Sub-decision:** the caller's raw input is **not** echoed into the entry by default. It would roughly double storage and duplicate what the snapshot already proves. An opt-in `SHADOWGRAPH_JOURNAL_ECHO_INPUT=1` is deferred to a later phase.

#### D5 — Ordering: `at` is NOT sufficient; a monotonic `seq` is required

Three independent reasons:
1. `now()` is injectable and tests pin it to a constant, so many entries legitimately share one `at`.
2. `Date.now()` ties occur naturally within a millisecond.
3. `id()` is `Date.now()` + 6 random base36 chars — **not** monotonic, so ids cannot order entries either.

`seq` is a per-graph integer assigned at append time, persisted in the journal, and restored on import as `max(seq) + 1`. Equal `at` values are ordered by `seq`; `seq` is unique and total. Ties are therefore impossible by construction.

#### D6 — Atomicity: guaranteed by co-location, not by a protocol

The journal lives **inside the same payload as the state** and is written by the same operation:
- **JSON:** `exportData()` serializes state and journal together; `save()` does one temp-write + `rename()`. Atomic by construction.
- **SQLite:** `save()` runs `BEGIN IMMEDIATE` → `replaceRelational()` (which rewrites `shadowgraph_events` alongside every other table) → `COMMIT`. Atomic by construction.

**So "one succeeded, the other failed" cannot happen** — and the design rule that keeps it that way is: **never persist the journal through a separate file, table-write, or transaction from the state.** If a future phase adds a separately persisted journal table, this guarantee is void and a two-phase protocol becomes mandatory.

The residual failure mode is different and benign: a crash between an in-memory mutation and the next `save()` loses **both** the state change and its entry, together. That is consistent, not divergent.

#### D7 — Idempotency

Today `idempotent()` returns the cached result and **short-circuits before any mutation**, so no entry is written on a replay — correct by default.

The subtle risk is rebuild: if the idempotency map is not restored, a post-rebuild retry with the same key would execute again and append a second entry. Therefore `idempotencyKey` is recorded on the entry that first performed the operation, and rebuild reconstructs the map from `(type, idempotencyKey) → payload`. This makes idempotency survive a rebuild without journalling the cache itself as a separate entity.

#### D8 — Rebuild

```
rebuildProjection(entries, options?) -> {
  ok: boolean,
  projection: { schemaVersion, records[], facts[], relations[], idempotency[] },
  rebuildable: boolean,
  reason?: string,
  replayedFrom: number,   // first seq replayed
  replayedTo: number,
  skipped: [{ seq, type, why }]
}
```

Pure: no I/O, no clock, no randomness, no dependence on `createShadowGraph` internals. `reviewSignals` are **not** rebuilt by replay — they are regenerated by calling `review()` on the rebuilt projection, which is what makes them a projection rather than state.

**Equivalence check (X-3):** canonical-JSON compare `rebuildProjection(journal).projection` against live `exportData()` with `events`/`reviewSignals`/`revision` excluded. Keys sorted; arrays ordered by `id`. If they differ irreconcilably, **ADR-0001 is wrong and must be superseded** rather than forced.

#### D9 — Migration: rebuildability starts at an explicit boundary, and history is never fabricated

**The honest constraint:** existing events carry `{id, type, at, project, recordId}` and no payload (G4, proven). They **cannot** be replayed into state. Claiming retroactive rebuildability would be fabrication.

Design:
1. Bump `SCHEMA_VERSION` to **3**.
2. On first open of a v2 store under the journal flag, write exactly one **`projection.baseline`** entry at `seq = 1`, whose payload is the *current* full projection, explicitly labelled `derivedFrom: "live_state_at_migration"`, **not** `"replayed_history"`.
3. Retain every pre-existing metadata-only event verbatim, re-typed `legacy_metadata_event`, `replayable: false`, sitting **before** the baseline.
4. `journalEpoch = <seq of the baseline>` is recorded in metadata. Rebuild replays only `seq >= journalEpoch`.
5. If a caller asks to replay across the epoch, `rebuildProjection` returns `ok: true, rebuildable: false, reason: "pre-epoch metadata-only entries are not replayable"` — it **must not** silently return an empty or partial graph. That is the anti-fabrication rule in code.

So: pre-migration decisions keep their audit breadcrumbs, the baseline is honestly labelled as reconstructed-from-state, and everything after the epoch is genuinely rebuildable.

#### D10 — Import / export of old and new journals

- Entries are exported as-is; `schemaVersion` per entry plus `journalEpoch` in metadata.
- **Unknown `type` or `schemaVersion` newer than supported:** retain verbatim, mark `unsupported: true`, **never drop and never crash** — dropping is silent data loss, crashing makes a newer file unopenable.
- `validate()` reports `unsupported_journal_entry` and `journal_gap` (see D11) so problems are discoverable, consistent with the G3 precedent of *report, don't rewrite*.
- `rebuildProjection` refuses (`rebuildable: false`) when unsupported entries fall inside the replay range.
- Upcasting uses the three strategies Microsoft documents (S10): tolerant deserialization for additive change, per-entry versioning, chained upcasters on read.

#### D11 — Purge

**Tombstone (default).** Appends `project.purged`, and rewrites that project's earlier entries to `payload: null, redacted: true` while keeping `seq`/`type`/`at`/`project`/`entityId`. Rebuild after a tombstone yields the graph minus that project, with the skeleton still auditable. `seq` stays contiguous.

**Hard purge (explicit, non-default).** Physically removes the entries. This **creates a `seq` gap**, so:
- rebuild must tolerate gaps — it does, because a fold over snapshots has no chain dependency;
- `validate()` reports `journal_gap` with the missing range, so the discontinuity is declared rather than hidden;
- referential integrity: relations pointing at purged entity ids must be removed in the same operation (`purgeProject` already does this for live state; the journal must match).

This is exactly why the terminology is **"append-oriented with documented deletion semantics"** and never "append-only".

**Scope note:** implementing purge behaviour itself belongs to **G5**. G4 only defines the journal's shape for it and adds the `journal_gap`/`redacted` handling. If the split feels cleaner the other way, G4-F can be deferred wholesale into G5.

#### D12 — Rollback

`SHADOWGRAPH_JOURNAL=1`, **default off**. Journal fields are additive; the existing `events` array is untouched until G4-E. Disabling the flag restores byte-identical current behaviour. Each sub-phase (G4-A…G4-G) is an independently revertible commit. If equivalence (X-3) fails, revert the G4-C/D commits and keep the contract + fixtures, which retain value as documentation.

#### D13 — Size and performance: the X-2 threshold, declared in advance

Measure `rebuildProjection` wall time and journal bytes at **1k / 10k / 100k** entries on this machine (Node v24.18.0).

**Add snapshots/compaction only if either fires:**
- rebuild p95 **> 250 ms at 10k entries**, or **> 1 s at 100k**; or
- journal bytes **> 10×** the live projection bytes at 10k entries.

Below those, snapshots are unjustified complexity. **No snapshotting is built in G4** — G4-G measures and reports, and a separate decision follows.

#### D14 — Security: the G2 bypass must not reopen

Four binding rules:
1. An entry's `provenance` describes **who performed the write**. It is *not* evidence about the claim, and it never elevates `verificationStatus`.
2. A journal entry asserting `sourceClass: 'human_confirmed'` yields a fact that is still `unverified`. The provenance contract's §2 rule ("no input can produce `verified`") applies to journal input exactly as it applies to `addFact` input — a journal file is caller input.
3. Because rebuild is a **fold over snapshots** and runs no domain logic, it cannot *newly* mint a `verified` fact. But it can faithfully carry one that a legacy import already contained (contract §6, U-3). G4-D must assert exactly this: no rebuilt fact is `verified` unless the corresponding live fact is also `verified`.
4. Entries are subject to the same redaction as everything else; `redact()` must cover `payload`. **Currently it does not** — see the new blocker B-4 below.

#### Sub-decisions still open (do not implement without a ruling)

- **J-1** — is `projection.baseline` acceptable as an honestly-labelled reconstruction, or must pre-epoch data stay entirely outside rebuild scope?
- **J-2** — should `decision.aged` / `fact.expired` be journalled at all, given they are clock-derived and reproducible by re-running `maintain()`? Journalling them is safer; not journalling keeps the journal purely intent-driven.
- **J-3** — does `reviewSignals` staying outside the journal conflict with "review signals are persistent" in the PM baseline? They are currently persisted in storage, so this needs an explicit ruling.

## ADR-0002 — Preliminary recommendation: fix principle violations before new architecture

- **Status:** `accepted` (2026-08-25) — followed in execution: G1, G2, G3 were fixed as additive test-first changes before journal construction began, and the sequencing proved correct (the G1 fix was a precondition for the reconsideration behaviour G4's rebuild tests now depend on).
- **Date:** 2026-08-25

### Context

Three verified gaps contradict stated non-negotiable principles in `docs/shadowgraph-vision-scope.md`:

| Gap | Principle violated | Proof (T6) |
| --- | --- | --- |
| G1 — `review()` ignores stored facts | 5, "Reconsideration is first-class" | stored fact → **0** signals; same fact as argument → **1** |
| G2 — provenance self-assertable; `human-confirmed` auto-verifies | 3, "Provenance is data"; security doc's *"never promote an agent assertion to a verified fact"* | `source:'totally_made_up_source'` accepted; decisions have **no** provenance fields |
| G6 — `context()`/`search()` return unbounded bare arrays | 2, "No silent omission" | completeness-key scan → `false` |

🟧 **SELF-DESCRIPTION** (source S19): `threadline-core` already enforces the G2 guarantee — *"Each transition… is **evidence-gated**: the server rejects self-assertion with a `ValueError`."* 🟧 (S20): `agent-logbook` *"refuses to write and hands back the conflict instead of silently overwriting."* These establish the pattern is implementable and shipped elsewhere; they are **not** evidence that ShadowGraph's specific design is correct.

### Decision (preliminary)

Sequence the program by **principle-violation severity, not architectural elegance**. Fix G1, G2, G6 as additive, test-first changes before journal construction (ADR-0001) begins.

Rationale: a system advertising guarantees it does not enforce is a correctness and trust defect. It also **invalidates measurement** — benchmark phase D ("changed fact triggers reconsideration") can currently only pass by the harness supplying the answer as an argument, which measures nothing.

### Limits of this recommendation (user directive 6)

- The evidence is **internal** (this repo's own probe output T6) plus the project's own stated principles. That is strong for "current behaviour contradicts documented principles" and says nothing about optimal sequencing under external constraints such as a release deadline.
- The competitor evidence is 🟧 self-description from READMEs. **Nothing was installed or tested.**
- No user-impact data exists — there is no telemetry establishing that real agents hit G1 in practice, only that the code path cannot work as documented.
- **G2's fix is a breaking behavioural change** and the compatibility strategy (below) is unvalidated against real stored data.

### Options considered

- **A. Fix S1 violations first, then journal** — ✅ chosen.
- B. Journal first, violations after — ❌ rejected: prolongs the period where the product misrepresents itself, and G1's fix should inform what fact-observation entries must carry.
- C. Both at once — ❌ rejected: unreviewable diff against a working system, no clean rollback point.

### Consequences

G2 becomes a **breaking change**: `source` closes to a fixed vocabulary; `human_confirmed`/`production_verified` become non-self-assertable. Mitigation: unknown strings → `agent_claimed` with the **original label preserved verbatim** in an audit field (security doc: *"preserve the original source label for audit"*), plus a CHANGELOG entry and migration note. Existing stored data must not be rewritten in place without a backup.

## ADR-0003 — Tool count is not solved by more compacting; deferred loading and code execution are out of scope for this release

- **Status:** `accepted` (2026-08-25) — held. No client-side deferred loading or code execution was built. The in-scope part was done: tool names/descriptions now carry the envelope and content-field contracts inline, and MCP enums are generated from the core vocabularies so a schema cannot drift from enforced behaviour. Protocol currency remains **deferred** as scheduled maintenance, documented honestly in `docs/mcp-compatibility.md` — the server states `2024-11-05` and claims nothing newer.
- **Date:** 2026-08-25
- **Directive basis:** user directives 4, 5, 6

### Context — why compacting is the wrong lever

🟦 **PRIMARY-VENDOR** (S6, anthropic.com/engineering/advanced-tool-use): 58 tools across five servers ≈ **55K tokens** *"before the conversation even starts"*; mechanism is `defer_loading: true`, where *"Deferred tools aren't loaded into Claude's context initially."*

🟨 **INDEPENDENT** (S9, aimultiple.com): code execution vs regular MCP — **78.5% fewer input tokens** (165K vs 771K), **77.4% net** reduction, output tokens **2.2× higher**, tool definitions **~15,400 vs ~3,300 per call**, 100% success both arms.

🟦 **PRIMARY-VENDOR** (S7, programmatic tool calling docs): *"improved performance by an average of **11%** while using **24% fewer input tokens**"* on BrowseComp and DeepSearchQA.

❌ **UNVERIFIED — explicitly excluded from this ADR** per directive 5 (all traced to YouTube descriptions or unattributed blogs, no primary source reachable): "77k → 8.7k / 85% reduction", "95% of context window preserved", "Opus 4 49% → 74%", "Opus 4.5 79.5% → 88.1%", "43,000 → 27,000 / 37%", "98.7% reduction", "Cloudflare 2,500+ endpoints → 2 tools", "30–40% latency".

🔻 **Withdrawn claim:** my earlier assertion that *tool count measurably harms accuracy* rested entirely on the unverified Opus figures. **That claim is withdrawn.** The only surviving accuracy datum is 🟦 S7's +11%, which measures programmatic tool calling — a different mechanism.

### Decision

1. **Do not pursue further tool-count reduction as the token strategy.** Compact mode (23 → 10 tools) trims a front-loaded cost linearly by removing capability, while the ecosystem's answer removes it structurally *without* losing capability. Direction is supported by 🟦 S6 + 🟨 S9; no specific percentage is claimed.
2. **Keep existing compact mode** as a tested compatibility surface. Do not invest further in it.
3. **Deferred loading (`defer_loading`) and code execution / programmatic tool calling are OUT OF SCOPE for the current release.** Reasons: both are **client/API-side** capabilities (S6/S7 describe them as Claude Developer Platform features configured by the API caller, not MCP server features); implementing a ShadowGraph-side equivalent duplicates client function; and the security doc forbids expanding MCP capability without separate review. ShadowGraph's obligation is a clean, well-described tool surface that behaves well *under* those client features.
4. **One actionable design consequence** — 🟦 **PRIMARY-VENDOR** (S8, tool-search-tool docs): tool search matches on *"tool names, descriptions, argument names, and argument descriptions"*. So tool naming and description quality directly determine discoverability under deferred loading. This is a **documentation-quality** task, not an architecture change.
5. **Protocol currency is scheduled maintenance, not an emergency.** Before any code change, empirically test whether a current client still negotiates `2024-11-05` (X-1). **No MCP code modified now** (directive 4).

### Options considered

- **A. Keep compact mode; defer client-side techniques; verify X-1; treat protocol currency as scheduled** — ✅ chosen.
- B. Minimise to ~6 workflow tools now — ❌ rejected: unmeasured, loses capability, and violates the brief's own guardrail *"do not approve a redesign solely because it lowers the first prompt token count."*
- C. Build a ShadowGraph-side code-execution surface — ❌ rejected: duplicates client capability; security doc requires separate review.
- D. Migrate to `2026-07-28` immediately — ❌ rejected for now: backward compatibility is specified (S1), X-1 is unverified, and directive 4 forbids touching MCP code. Revisit once X-1 is measured.
- E. Ignore the protocol gap because tests pass — ❌ rejected: local tests cannot detect client negotiation failure.

### Consequences

The brief's headline concern — "first MCP session costs more tokens than a plain answer" — is **real but largely not ShadowGraph's to solve**; it is a property of how clients load tool definitions. The honest framing is therefore total warm-lifecycle economics (A–E), as the benchmark plan already argues. This ADR **removes** an assumed workstream and adds one small documentation task (item 4).

## ADR-0004 — Preliminary recommendation: benchmark against a no-memory baseline only

- **Status:** `accepted — provisional` (2026-08-25). The **policy** is accepted and binding: never benchmark against competitors, always include a no-memory baseline, do not use LoCoMo. The **warm-task token/cost benchmark it specifies is NOT implemented** — only the journal performance benchmark exists (`scripts/bench-journal.mjs`). No token, cost, latency, or tool-call figure is claimed anywhere in this repository. Provisional because the policy has therefore been *adopted* but not yet *exercised*.
- **Date:** 2026-08-25

### Context

Primary-source record (S12 blog.getzep.com, S13 github.com/getzep/zep-papers issue #5, both accessed 2026-08-25):

1. Mem0 published arXiv **2504.19413** claiming SOTA on **LoCoMo** (arXiv **2402.17753**).
2. Zep rebutted: LoCoMo flawed **and** Mem0's Zep implementation wrong — *"assigned the user role to both participants"*, timestamps appended to message text rather than the dedicated `created_at` field, searches run serially not in parallel. Zep's corrected figure: **75.14% ± 0.17 vs Mem0 Graph ~68%**.
3. Zep **corrected its own arithmetic** on that number: *"in an earlier version of this article, we erred in how we calculated Zep's LoCoMo score."*
4. Mem0 counter-alleged (S13) that Zep's separate **84%** was really **58.44%** — *"a denominator that excluded Category 5 questions while including Category 5 correct answers in the numerator."*
5. Thread **closed due to inactivity**. Unresolved.

LoCoMo's documented flaws (per S12): conversations average **16k–26k tokens**, inside a modern context window; **it does not test knowledge updates**; dataset quality issues. And, quoting Mem0's own paper: *"Mem0's own results show their system being outperformed by a simple full-context baseline."*

### Decision (preliminary)

1. **Never benchmark a competitor's product.** Arms: no-memory baseline · current ShadowGraph · redesigned ShadowGraph.
2. **Always include a full-context / no-memory baseline**, and publish it winning if it wins.
3. **Do not use LoCoMo** as a primary metric — it cannot measure fact revision, which is ShadowGraph's core.
4. **Pre-register rubrics** before running; publish the failure/omission log.
5. **State what n=10 cannot support.** No SOTA claims; paired deltas and directional signal only.
6. Phase D is the differentiating measurement — and per ADR-0002 it is not honestly measurable until G1 is fixed.
7. Evidence = persisted state and tool results, never the assistant's prose.

### Limits of this recommendation

- This is **methodology guidance, not a validated protocol**. It has not been executed once.
- Rubric design, inter-rater reliability, and LLM-as-judge caveats are **not** yet researched — two `web_search` calls on evaluation methodology failed with backend 403s.
- **No calibration methodology was verified** this session (ECE/Brier/beta-binomial): ❌ unverified. P5 depends on it.
- LongMemEval's licence, size, and local runnability: ❌ unverified.
- No token/cost measurement has been performed at all, so the cost model underlying "warm-lifecycle economics" is untested.

### Options considered

- **A. Baseline-only, pre-registered, negatives published** — ✅ chosen.
- B. Benchmark against mem0/Zep/threadline-core for positioning — ❌ rejected: the primary record shows both prior attempts produced public arithmetic errors and reputational damage; implementing a competitor at its best requires their expertise.
- C. Adopt LoCoMo/LongMemEval for comparability — ❌ rejected for LoCoMo (no knowledge-update testing); LongMemEval deferred pending verification.

### Consequences

ShadowGraph cannot claim to beat named competitors. It can claim measured self-improvement and publish an honest protocol — which `research-log.md` §8.1 identifies as unoccupied ground. Publishing negative results is a credibility asset here.

## ADR-0005 — Narrow the differentiation claim to two capabilities

- **Status:** `accepted` (2026-08-25) — both claims are now implemented and tested. **Deterministic reconsideration over stored state** (G1: `review()` reads stored facts, survives restart, verified across four restarts in test `R3`) and **first-class falsification conditions via `reopenWhen`** (project-scoped, superseded-fact aware). "Moat" language is absent from the repository. Retrieval quality remains a deficit rather than a differentiator, as this ADR stated.
- **Date:** 2026-08-25
- **Directive basis:** user directive 6 (narrow to the two named claims; avoid "moat" language without clear research support)

### Context

🟧 **SELF-DESCRIPTION** (S19–S22, READMEs accessed 2026-08-25; **nothing installed or tested; no star counts verified**): at least four local-first SQLite MCP decision-memory servers exist — `threadline-core` (17 tools, Apache-2.0, evidence-gated transitions rejecting self-assertion), `agent-logbook` (supersession chains, conflict-refusal), `pmb` (rebuildable indexes, no LLM on the read path), `sqlite-memory-mcp` (FTS5 + BM25 + sqlite-vec via RRF, provenance tracking, *"reviewable consolidation instead of silent memory rewriting"*).

⚠️ **SECONDARY** design-rationale literature (S17/S18): a ~30-year field — IBIS/gIBIS, PHI, QOC, DRL, RATSpeak, Compendium — whose documented central failure is capture cost: *"Recording the reasoning process of design can be very time-consuming and expensive"*, producing *"cognitive, capture, retrieval, and usage limitations"* plus organizational ones. Burge & Brown's **`InfoRat`** already performed *"inferences over a design's rationale in order to detect inconsistencies and to assess the impact of changes"* — i.e. ShadowGraph's `reconsider`, decades earlier.
⚠️ **Citation caveat:** *Horner & Atwood, CACM 37(1):92–105, 1994* comes from a secondary reference list; the original was **not opened**; volume/pages **unconfirmed**.

### Decision

**Differentiation is narrowed to exactly two claims** (user directive 6):

1. **Deterministic reconsideration over stored state** — rule-based, automatic reopening of decisions from *persisted* facts, with no LLM in the decision path. No surveyed competitor README advertises this. **Currently broken (G1); the claim is aspirational until G1 is fixed and tested.**
2. **First-class falsification conditions via `reopenWhen`** — a decision that carries, as structured data, the conditions under which it must be revisited.

**Dropped as differentiators** (table stakes in this cohort): local-first SQLite storage; zero runtime dependencies; JSON/SQLite dual backend; "compact lossless MCP"; supersession chains; failed-attempt memory; provenance tracking.

**Supporting but not differentiating:** the graded four-class provenance lattice (`threadline-core` already does binary evidence-gating — finer-grained, not novel); honest warm-lifecycle benchmarking (`pmb` gestures at the same idea).

**Positioning thesis to record in the vision doc:** rationale capture historically failed because *humans* would not pay the capture cost; an agent already articulating its reasoning drives that cost toward zero. **Honest corollary:** ADR-0003's evidence shows tool-definition tokens are a *new* capture cost — the barrier moved from human attention to context budget rather than disappearing.

**Language discipline:** the word **"moat"** is not used. These are *differentiating capabilities relative to four surveyed READMEs* — a bounded claim, not a defensibility analysis.

**Retrieval quality is a deficit requiring work, not a differentiator:** ShadowGraph has no FTS5, no BM25, and an `O(n)` full-JSON-stringify search matching schema key names (G7 — `title`, `confidence`, `schemaVersion` all produced false positives), while 🟧 S22 ships FTS5+BM25+RRF.

**Study `InfoRat` and QOC before designing `reconsider`.** Cite prior art; do not reinvent.

### Options considered

- **A. Narrow to the two named claims; adopt capture-overhead thesis with its corollary; treat retrieval as a deficit** — ✅ chosen.
- B. Keep broad first-mover claims — ❌ rejected: contradicted by four live repositories.
- C. Pivot to competitor parity (vector search, RRF, consolidation) — ❌ rejected: chases parity over the distinctive capability; the brief forbids demolishing working parts to imitate another product.
- D. Add FTS5 immediately — ⏸️ **deferred, not rejected.** Correct direction, but `node:sqlite` is ✅ **stability 1.2 Release Candidate** (S14), not stable, and JSON remains a supported backend, so FTS5 cannot be the only search path.

### Consequences

Marketing claims shrink substantially; defensibility of what remains rises. A retrieval workstream is added that the briefs did not contemplate. `reconsider` gains citable intellectual lineage. Claim 1 is **contingent on fixing G1** — it must not be published before then.
