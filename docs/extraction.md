# Extraction activation and operation

This page describes the retained Claude route. The optional explicitly selected
Codex subscription route has its own [terminal setup guide](codex-integration.md).
Neither route transfers legacy captures to a newly selected provider.

Extraction is a one-shot owner CLI worker. Capture requests it after an eligible Stop or SessionEnd by spawning a detached, unreferenced process with ignored standard streams. Capture never waits for a model call. That process gets only the environment names the executor passes to its own child plus `SHADOWGRAPH_*` configuration, never the rest of the hook's environment: a Claude Code desktop session sets its own provider route (`ANTHROPIC_BASE_URL`) and session tokens in every hook, which the executor would refuse (`provider_environment`). Your settings' `env` and `apiKeyHelper` are still checked, and the child's own `auth status` must still report the first-party subscription route. Two variables are not filtered but refused: a hook whose session runs under another profile (`CLAUDE_CONFIG_DIR`) or a session token (`CLAUDE_CODE_OAUTH_TOKEN`) does not start the worker at all, because the worker would run under your default profile's account, which may not be that session's (`session_profile_selected`). Explicit `shadowgraph extract` still refuses those variables in its own environment. A desktop host names its session's account in every hook (`CLAUDE_CODE_USER_EMAIL`); a session whose account is not the bound one does not start the worker either (`session_account_differs`). Activation binds the account: it keeps a digest (never the values) of the identity fields the executor's `auth status` reports under your default profile, keyed per activation — the key is stored beside it, so this prevents linking activations, not a dictionary check by someone who can read the file — and every invocation compares it before any model call, so a different account, or one `auth status` no longer names, is refused (`activated_account_changed`); a host whose `auth status` names no account cannot be activated (`extraction_account_unidentified`). An activation recorded before this binding is not run; activate again. Fresh capture provenance is required by the production worker. Unsupported profiles or session tokens are refused before capture; a known mismatched session account is refused too. A session without account metadata can be captured locally but remains unbound and is held from automatic extraction. Legacy, unknown-origin, foreign-account and prior-activation captures are not silently relabeled or drained. Session identity uses the account e-mail supplied by the host, not every possible organisation/account identifier. The account can still change between the check and the invocation. `tools/automatic-e2e/run.mjs` checks this path end to end in isolation, with a stand-in host program and no model. Delivery, MCP and HTTP do not invoke or activate extraction. There is no extraction listener or daemon. Detached survival on a particular host must be measured; if it is not verified, use explicit `shadowgraph extract` and narrow the automation claim.

## Activate only after the extraction gate

### Obtain the profiled Windows executor

The Windows x64 Claude Code 2.1.292 executable is available from Anthropic's public download service. It is not necessary to obtain another user's private binary or credentials. Download it to a dedicated, owner-chosen directory rather than replacing the interactive host:

```powershell
$executorDirectory = Join-Path $env:LOCALAPPDATA 'ShadowGraphExecutor/2.1.292'
New-Item -ItemType Directory -Force -Path $executorDirectory | Out-Null
$executorPath = Join-Path $executorDirectory 'claude.exe'
Invoke-WebRequest 'https://downloads.claude.ai/claude-code-releases/2.1.292/win32-x64/claude.exe' -OutFile $executorPath
$expectedHash = 'eb95bb65955f8b1702e800815f9a2c0388a5de0f196c354c7ee1dd5cb9a2ba23'
if ((Get-FileHash -Algorithm SHA256 $executorPath).Hash.ToLower() -ne $expectedHash) {
    throw 'Executor checksum mismatch; do not run this download'
}
& $executorPath --version
```

The checksum is also published in the [vendor manifest](https://downloads.claude.ai/claude-code-releases/2.1.292/manifest.json). Availability and an exact checksum establish the binary's identity, not its isolation or account suitability. This profile still requires successful host validation for the exact installed ShadowGraph runtime, the existing first-party subscription, disabled overage, and the terminal activation confirmation below. Newer versions and other platform builds are not substitutes for this profile. Do not copy credentials between Windows users or profiles.

### One-time setup and automatic operation

Install a packed runtime, install its delivery/capture hooks, activate delivery and capture for the same private store, and confirm the project's binding using the [integration instructions](../integrations/README.md). Activate extraction only after its host gate passes. These setup actions require their existing owner confirmations; MCP proposals do not grant activation or binding authority.

After setup, supported Stop/SessionEnd events request automatic extraction. Ordinary work does not need a memory reminder or a manual `extract` command. Capture being present does not establish successful extraction, and extraction being successful does not establish that a later model received or used the record. Check the processing state and scoped delivery evidence for each stage. The current candidate has not yet established the complete automatic Desktop-to-fresh-session acceptance episode; a manual extraction demonstration is not a substitute.

Cross-profile/account capture remains a release blocker for a general automatic-memory claim: declining a foreign session's automatic trigger does not prevent its previously captured material from entering a later drain. A synthetic run confined to one fresh project and account does not resolve that boundary. Do not enable standing extraction on the strength of that bounded run.

Prepare and verify the exact packed runtime before requesting approval. A real runtime replacement, activation and first real model call require the owner's explicit gate approval. The command records evidence, the exact shared runtime/store, the resolved executor configuration, frozen budgets and a new activation identity:

```text
shadowgraph activate extraction --evidence <receipt> --store <private-store> --runtime <pinned-runtime> --executable <absolute-Claude-executable> --model <model> --no-overage-confirmed true [--host-validation <host-validation-receipt>]
```

**Current hosts (runtime-evidence profile).** Any other Claude Code 2.x host from 2.1.288 on runs on the runtime-evidence profile (`claude-code-runtime-evidence-v1`), not on a pinned binary. Its rules:
- You select the extraction model explicitly with `--model`: `claude-haiku-5-5`, `claude-sonnet-5-5` or `claude-opus-5-5`. Choose the least costly one that extracts your work adequately. Any other choice is refused (`model_not_selectable`).
- Every invocation streams the host's own account of the session (`--output-format stream-json --verbose`). Its output is used only when that account shows the confined session the flags ask for:
  - no tool but `StructuredOutput`;
  - no MCP server, slash command, skill or non-builtin plugin, each of these fields present;
  - `apiKeySource` `none`;
  - the selected model and the checked host version;
  - no hook run;
  - no other tool call;
  - only `firstParty` usage.

  Anything else is `runtime_confinement_unverified`, and nothing is recorded.
- The host may update in place; the executable path, model, profile and account stay bound to the activation.
- It runs the quoted recipe with corrections, as the Codex route does.

Setup, sharing and the CLI account rule are in the [Claude Code CLI guide](claude-code-integration.md). The pinned profiles below are unchanged.

`--executable` names the Claude Code program itself; on Windows that is its `.exe`, and a `.cmd` or `.bat` shim is refused (`executable_unavailable`). The owner must confirm subscription-only operation with no overage on every activation. Outside synthetic scratch locations the terminal also asks for confirmation of the exact configuration. There is no API-key, proxy, alternate-provider or paid fallback. The executor is pinned to its supported host/configuration profile and model: it runs only on Windows, with Claude Code 2.1.288, the host version its restrictions were first verified against, or with the one Claude Code 2.1.292 binary its profile names (`src/internal/extraction-contract.js`). On any other platform, host version or binary it is refused (`policy_platform_unverified`, `host_version_unverified`, `host_binary_unverified`). A 2.1.292 activation also needs `--host-validation <receipt>`: the receipt of a passing real-host validation of that binary under the installed runtime, covering confinement, routing, recursion and shutdown. Without it the activation is refused (`extraction_host_validation_required`), and a receipt for another binary, another runtime or with any check not passed is refused too (`extraction_host_validation_mismatch`). The version string and the configuration check are prerequisites, never that validation.

Administrator policy refuses extraction on its existence alone (`managed_policy_present`): the system managed-settings files and folders, Windows registry policy, and the remote policy cache `~/.claude/remote-settings.json`. A remote cache of at most 5 bytes is not counted: it can hold at most `{}`, while the shortest object with any member is 6 bytes. The host writes such an empty cache for an account it reports ineligible. Only its size is read. A larger cache has one exception, on the pinned 2.1.292 binary only, which was traced not to fetch or apply it when its own `doctor` reports the account ineligible. On every host, extraction requires the host's `doctor` to exit successfully with exactly one remote-settings report, which must be exactly `Managed settings (remote): not fetched — requires an Enterprise or Team subscription`; any other report, or none, is refused (`remote_policy_unverified`). When the cache is the only policy source, that report is what lets extraction continue on 2.1.292. A cache that appears or disappears between the check and the invocation is refused (`configuration_changed_before_invoke`). The cache is only checked for existence, never read or changed. The check reports the cache's presence, the host's reported applicability and the unassessed policy conflict separately; the activation record keeps them as they were at activation, while every invocation repeats the check. Limits: the exception rests on the static trace of that one binary and on the exact wording of its report; a line in other wording saying the cache is applied would not be detected, and the account can still change between the check and the invocation.

The host-validation receipt is a JSON file: `kind` `shadowgraph-extraction-host-validation`, `version` 1, `hostVersion`, `binarySha256`, `runtimeCommit` (the installed runtime's commit), `checks` with `confinement`, `routing`, `recursion` and `shutdown`, each `pass` or `fail`, and optionally `validatedAt` (recorded as null when absent). It records a real-host validation run outside ShadowGraph against that binary and runtime: real extraction invocations through the installed executor that show the child neither loads instruction files nor reads, writes or runs anything (confinement); that a provider variable is refused before any process starts and only the subscription model answers (routing); that no ShadowGraph hook runs under the child (recursion); and that a stopped invocation leaves no process or scratch behind (shutdown). ShadowGraph does not perform or re-check that validation: at activation it checks only that the receipt names this host version, this binary and this runtime, with every check `pass`, and records the receipt's path and SHA-256. Whoever can write the owner's files can write such a receipt, so it is evidence the owner reviews at the activation's terminal confirmation, not a proof ShadowGraph verifies.

The executor repeats the restriction and subscription checks before each invocation and refuses a changed executable/configuration. Activation checks do not invoke the model. Capture must already be active for the same private store/runtime; an active delivery capability must match too. Live capture continues to require JSON; the internal worker and lifecycle safety are tested on JSON and SQLite, which is not a claim that live SQLite capture has been enabled.

On the pinned profiles the requested model remains `claude-opus-5[1m]`; on the runtime-evidence profile it is the model selected at activation. A result must report exactly one model-usage identity: that exact name or its bare ID without a context suffix. Other models, other suffixes and multiple identities are refused. This accommodates the host's context-suffix reporting without permitting model fallback; numeric usage is taken from the single accepted entry.

`shadowgraph extract --project <project>` or `--origin <origin>` is an explicit scoped drain. With neither argument, a workspace binding confirmed in the store is required. Read grants do not authorize extraction writes. Automatic drains consider covered project queues in the activated store; all scopes share one per-drain budget and the same per-user usage window. An excluded project or unattributed origin can only be selected explicitly by the owner. A manual-store environment override never replaces the activated destination.

## Budgets and status

The fixed ceilings are 65,536 input prompt bytes per item, two host turns per call (`--max-turns 2`; a call that needs more is stopped and blocked), four items and four calls per drain, 240 seconds of work, twelve calls per rolling hour, one retry with one second backoff, and 128 journal entries per captured session. Capture admission limits remain unchanged. Shutdown additionally allows bounded child termination and lease/status cleanup; filesystem latency is not a hard real-time guarantee. The usage file persists reservations outside memory stores and backups. Crashes and ambiguous results do not refund calls, and reactivation does not reset usage.

Capture inspection, normal read completeness and delivery expose the existing pending/processing/error fields. `extractionAvailable` is a fresh projection of configured extraction for the exact store and covered project, with no outstanding worker error or unsettled execution. It is false for a busy or unconfirmed execution, inactive/malformed configuration, another store, or a library graph without a host availability projection. The delivery `extraction` label reports active configuration separately. These reads do not probe model/service health, consume quota, start extraction, write operational state or grant access. Availability is never serialized into memory or restored from a backup. Historical errors remain visible until a successful worker status write clears them.

## Deactivate, uninstall and recover

```text
shadowgraph deactivate extraction
shadowgraph uninstall-hooks
```

Activation and deactivation serialize their final record changes under one short shared fence. Confirmation and host checks happen before taking that fence; activation rechecks the approved record inside it. Concurrent changes cannot overwrite another capability's deactivation or history. Deactivation persists the disabled state first. The worker checks it during a call, between items and before commit, terminates its local child, discards late output and leaves uncommitted items pending. An atomic commit already started cannot be undone by later cancellation. Cleanup waits for the worker lifetime fence, including child settlement. Uninstall also disables extraction when no hook entries remain. Neither operation claims to cancel a remote model request or erase provider bookkeeping.

A locked or unreadable store cannot re-enable extraction. Cleanup reports `deferred` when it cannot prove local settlement. Each host process has a bounded one-shot supervisor connected through private IPC. The supervisor validates its content-free identity and settlement path before reporting ready, and receives the host request only after the running marker is durable. If the worker dies before that request, it records proof that no host child started. If the worker dies during the request, the supervisor stops its own host child and writes content-free settlement proof. `extraction-worker` records the invocation identity and state; only matching proof permits automatic recovery after the usage fence and item lease expire. Raw prompts and output are not written to these operational files. An absent, mismatched or unconfirmed settlement remains blocked and cleanup reports deferred; preserve that evidence and reconcile the particular execution before restarting. The supervisor is detached so it can finish cleanup after its parent exits; it does not remain as a daemon. Cancellation allows up to two seconds for supervisor settlement in addition to bounded lease/status cleanup. Do not kill an unrelated process based on a stale PID or delete memory/control files to clear the condition.

## Source identity and compatibility

Before each invocation the worker registers a fresh dedicated session UUID, lease ID/window and an opaque correlation token in `extraction-invocations.json`. The registry is bounded to 128 rows and 64 KiB and stores no captured material. The session ID is passed through the supported host switch; the correlation token is passed in controlled invocation arguments and remains unchanged for an identical-prompt retry. Capture excludes S3 only for that dedicated invocation during its lease window. A user-session tool ID match or historical session list is insufficient. Missing or malformed attribution preserves user capture; an unavailable registry blocks a new model invocation. The restriction profile still disables child hooks and session persistence; actual host semantics require gate evidence.

The PR41 activation/trigger runtime requires the PR40 worker-budget floor and the generation and retention floors already documented. Earlier readers may preserve unknown metadata but do not enforce these operational semantics. Concurrent activation-record writers must all use the PR41 shared-record fence; do not run older activation/deactivation commands concurrently with this build. Before rollback, deactivate extraction, confirm cleanup and drain/reconcile outstanding leases. Never run an older worker against active extraction. Delivery/capture runtime changes must preserve exact shared-store/runtime checks. Prepare and approve the real re-pin before executing it.

Eligible uncited raw expires under retention even when quarantined. Expiry does not release quarantine or remove accepted experience and required cited evidence. Expired raw cannot be re-extracted. Backups and interrupted-restore recovery files may retain material removed from the active store; this is a documented activation limitation, not complete physical erasure. These commands do not delete those copies or modify the protected restore primitives.
