## Creation-ID migration

Ordinary creation generates canonical IDs and refuses supplied creation `id`
fields before lookup, retry or NOOP handling. Capture returned IDs for later
references; keep `idempotencyKey` as a separate retry identity. Nested
alternatives and every memory-plan envelope/operation follow the same policy.
Stored IDs, validated import/restore and replay are preserved. See the
[creation identity contract](contracts/creation-identity.md) for entry points,
batch behavior, migration examples and the older-binary rollback limitation.

## 2. Instance methods

### Writing

| Method | Notes |
| --- | --- |
| `addDecision(input)` | Records a decision with alternatives, assumptions, evidence, provenance. Alternatives are part of the decision, not independent entities. |
| `addAttempt(input)` | Records an attempt and its lesson; its `causalClaim` is derived from `reason`. |
| `remember(input)` | Reconciles one exact `(project, scope, memoryType, key)` identity and returns `ADD`, `UPDATE`, or `NOOP`; update retains the previous version. Idempotency is isolated by that full identity. |
| `applyMemoryPlan(input)` | Preflights and applies explicit `ADD` / `UPDATE` / `DELETE` / `NOOP` operations. Delete invalidates rather than erasing historical payloads. |
| `addFact(input)` | **Rejects `verificationStatus: 'verified'` / `'expired'`.** Unknown `sourceClass` downgrades to `agent_claimed` with `sourceRaw` retained. Supersedes any prior fact for the same `(project, key)`. |
| `setOutcome(id, outcome, scope)` | Records an outcome and applies one evidence-weighted confidence contribution. |
| `addConfidenceEvidence(input)` | Applies a keyed contribution. Re-applying the same key is a no-op — this is the double-count guard. |
| `updateDecisionStatus(id, status, scope)` | Accepts any of the thirteen states plus formatting aliases; stores the canonical form. Throws `Invalid decision status: <raw>` otherwise. |
| `supersedeDecision(input)` | Supersession inside the input's own project (or origin) with a persisted `supersedes` relation; a missing decision or replacement, or one outside that scope, is refused alike (`Supersession requires two existing decisions`). |
| `link(input)` | Explainable relationship. The write names its `project` (or, with none, its `originId`; with neither it is refused with `write_scope_unresolved`), and both endpoints must exist inside it: an endpoint in another project, in legacy data or of another origin is refused exactly like a missing one, so no relationship across projects is created. One stored across projects earlier is kept. The relation ID is generated in the global entity namespace; caller-supplied creation IDs are refused before endpoint lookup. |

A by-id change -- `setOutcome`, `addConfidenceEvidence`, `updateDecisionStatus`, `supersedeDecision`, `verifyFact`, `acknowledgeReview` -- changes only what its own write scope owns: `project`, or with none `originId`, given in the input object or as the trailing `scope` argument. An id of another project, of legacy data or of another origin gets exactly the error an id that does not exist gets (`Decision not found`, `Fact not found`, `Review signal not found`), and with neither a project nor an origin the call is refused with `write_scope_unresolved` before any id is resolved. Reading more never allows writing more.

### Reading — all return `{ items, page, completeness }`

`search(query, options)` · `retrieve(query, options)` · `recall(query, options)` · `memoryHistory(options)` · `getJournal(options)` · `legacyAttributionReview(options)`

`recall()` unions lexical, vector, graph-distance, and temporal candidate lists and applies weighted RRF. It returns response-level `signals`/`ranking` plus per-hit `ranks`, raw `scores`, and reasons. A missing or model/dimension-incompatible vector is declared with `semantic.available=false`; `semantic.indexed` counts the candidates carrying a stored vector, with or without a query vector. `search()`, `retrieve()`, `recall()` and `context()` are `project_only`: with `project` they read only what that project owns, and a record written before schema 6 in `default`, or with no project, belongs to no project a caller can name, so none of them returns it; with no project but an `originId` they read only that origin's unattributed records; with neither they read nothing, never every project and never the `default` project. `retrieve()` adds graph neighbours, and `recall()` ranks by graph distance, only through records inside the same boundary. Memory records also require an exact scope match, and an omitted scope means the all-null scope. Supplied projects must be non-empty strings, scope accepts only string/null `userId`/`agentId`/`runId`, and `asOf`/`currentAt` must be valid timestamp strings/null. Valid-time selection and temporal ranking compare parsed instants, so timezone-offset forms do not change ordering. `memoryHistory()`, `getJournal()`, `stats()`, `getReviewSignals()`, `redact()`'s output and the public `exportData()` read inside the same boundary. `getJournal()` lists only entries about what the scope owns -- never a whole-store projection baseline -- and positions in `completeness.gaps` only the gaps the scope's own hard purges explain; it always carries `completeness.limitation` (`scoped_coverage`). Scope coverage reports the resolved request state and limitations; MCP input/output schemas describe this boundary.

`legacyAttributionReview(options)` is the administrative view of legacy data whose owner is uncertain, and the one read that returns it: every record and fact written before schema 6 in `default` (`attribution: 'legacy_ambiguous'`) or with no project (`'legacy_unattributed'`), before and after `migrateAttribution()`. A record the migration has not reached yet (`migrated: false`) is shown with the attribution the migration's own mapping gives it, decided from what is stored and the recorded absence of a project, never from content. Each item is `{ id, kind, attribution, migrated, assignedProject: null, entity }`, where `entity` is the canonical record, unsummarised. It is not a project and takes no scope: the real project `default`, every named project, a record of an explicit project and origin-owned records never appear in it. Nor does a record or fact from a newer schema than this build reads, whatever it stores: it is kept as it arrived, the migration skips it, and `validate()` reports it as unsupported. It writes nothing. It pages by `limit`/`offset` like every read here, with `completeness.scope` `{ view: 'legacy_attribution' }`. Reassigning such a record is later work, and no CLI, HTTP or MCP surface exposes the view yet.

`context(input)` is the default-path read: it returns named collections (`activeDecisions`, `staleAssumptions`, `failedAttempts`, `firedConditions`, `belowConfidenceThreshold`, `conditionDiagnostics`, `reusableAttempts`) plus a `completeness.collections` breakdown, evaluates reopen rules, and persists nothing -- no review signal and no revision, on every surface (CLI `context`, HTTP `POST /context`, MCP `shadowgraph_context` and the `shadowgraph://context` resource). The one exception is a grant-bearing call, which commits the declared access audit like every grant-capable read. A read with query text that the fallback answers also records runtime misses (see Storage): kept in memory, and written by the process's next save or, on a grant-bearing call, by that call's save. The declared write budget of one delivery is `CONTEXT_DELIVERY_BUDGET` in `src/mcp-tools.js`, frozen before it was measured: an own-scope delivery makes no canonical write, journal entry, revision or save and takes no store fence; a delivery that presents an access key (a grant, or an `accessId` or `grantId` that is null) makes no canonical write or journal entry, and commits one revision through one save that rewrites the whole store and adds at most one audit aggregate per grant, surface, outcome and UTC day, and any runtime misses it recorded, with at most 4096 bytes of growth and 250 ms added per delivery. `node scripts/context-size.mjs --check` measures a delivery against it and fails when any category is exceeded; the budget is not raised to fit a measurement. Due decisions report a signal id only when one already exists; otherwise `reviewSignalStatus` is `unpersisted`. Its result carries a declared `notice` (`context_does_not_persist`) naming the replacement. `reviewContext(input)` -- CLI `review-context`, HTTP `POST /review-context`, MCP `shadowgraph_review_context` -- is the explicit evaluate-and-persist operation: it may create review signals, only for decisions of the project it reads, and every transport persists them before returning success. With no project selected either evaluates nothing, raises no signal and reports `project: null`, which is what the MCP context resource, having no project to name, returns. `failedAttempts` holds the attempts that failed: a declared or observed `resultClass` of `failed`, or, with no `resultClass` and not captured, a result worded as a failure. A captured attempt (one carrying a `captureRef` or `outcomeEvidence`, which only capture writes) with no `resultClass` is undetermined: held by no collection, `reusableAttempts` included, and counted as `undetermined` on that collection's completeness entry.

With a `query` or `focalId`, `context(input)` also returns `relevant`, placed before the collections. Every record inside the read boundary is ranked on the record itself by the hybrid engine (`recall()`'s, over the same boundary view), matching the text that engine indexes (not recorded condition rules): a record is relevant when the lexical, semantic or graph signal ranks it, whatever its status, outcome or conditions. Here a lexical match counts only through a content word: common English function words such as "the", "is", "what", "must" and "without" establish nothing, though every term still orders the records found. So a record that shares nothing else with the query is not relevant to it, and a query of function words only reports the lexical signal unavailable, as a blank one does; the head's lexical `matched` counts the records sharing a content word, while each item's ranks are computed over every term. A name, keyword, month or acronym that folds to such a word ("IT", "US", "May", "None", "Less") is dropped with it; another language's function words (Arabic "في", Spanish "el") can still establish relevance on their own; and a single shared content word, even a generic verb such as "use", still does. `recall()` is unchanged. Memories are those of the project-wide scope, as on every read without a memory scope, and a graph walk never passes through another scope's memory; facts and memories are those valid at `asOf`, or now when none is given, and recency orders the items, never selects them. No semantic signal is computed on this read: no request text is sent to an embedding endpoint, and `limitation` says so. The head -- `scope`, `relevance` (whether any signal established relevance, and each signal's availability), `fallback`, `byKind`, `total`, `returned`, `omitted`, `hasMore`, `complete`, `limitSource`, `limitation`, `temporal` (the asOf and the counts of items with an unknown event time or resting on the recording order only), `lines` (the claim class of each delivered line, and whether it requires expansion, in item order), `processing` and `expansion` -- precedes `items`. Each item is `{ tier, line | record, score, ranks }`: with `compact: true` a derived claim line (T1, `src/compact-tier.js`), otherwise the full record (T2) without its embedding; a line that cannot carry its decisive meaning is delivered as the full record, declared `fallback.reason: 'decisive_meaning_omitted'`. When no signal ranks any record, `items` is the working set in full (T2, `score` and `ranks` null), declared `fallback.reason: 'relevance_not_established'` with `complete: false`. `limit` bounds `items` as it bounds each collection. The relevance path writes no canonical state: a read with query text that the fallback answers records runtime misses (see Storage), kept in memory until the process's next save; `reviewContext()` does not take it. A `focalId` outside the boundary reaches nothing, like an unknown id. Each item also carries `temporalEvidence` (PR-29; plan v1.4.4 §17.5): `recordedAt`, `eventTime` (`known` with the time only when a fact's or memory's stored event time differs from its recording time, `unknown` otherwise, and always for decisions and attempts), and `currentState` at the read's instant (`null` for an attempt; otherwise `state` `current`, `historical`, `not_yet_valid`, `unresolved` or `undetermined`, `basis` `explicit_supersession`, `validity_window`, `recording_order_only` or null, at most ten `evidence` ids that decide it, and `evidenceOmitted`). When only the recording order tells two same-key versions apart, both are `unresolved`, and expansion leaves the pair unresolved too. A due review, a failure or a reconsideration does not make a decision historical; in an as-of read a decision's state is `undetermined`. The head's `temporal` gives the `asOf`, how many items have an unknown event time, and how many rest on the recording order only. Nothing is written.

`expand(input)` (MCP `shadowgraph_expand`; no CLI verb or HTTP route) takes a line's expansion handle -- `recordId`, `digest`, `asOf`, `derivationVersion`, `derivedAt`, null fields left out, with its `scope.project` as `project`, its `scope.grantId` as `grantId` and its `scope.originId` (present when the read resolved no project) as `originId` -- and an optional `maxExpansions` (0-50, default 5). It resolves the record only inside the boundary of the read that produced the line, the grant re-checked now, and derives it again exactly as a line is derived. `status` is `current` when the digests match; `revision_changed` when the record changed since, with `boundRevision`, `currentRevision` and the current record, never labelled as the old revision; `purged` when the first purge of the read's own project recorded after `derivedAt` was logical; and `unavailable` otherwise, a hard purge and a granted project's purge included (a purge narrows the grant). A record outside the boundary -- another project's, another memory scope's, an alternative -- answers exactly as an unknown id, so existence never leaks, and no summary stands in for a record that is not served. `investigation` lists the record's structural counterparts (facts of the same key in its project, supersession links), current rivals first, at least the budget and never fewer than ten, the rest counted in `omitted`; supersession links outside the read, or to nothing, are counted in `unreachableLinks` and make the answer incomplete. Each listed counterpart is `resolved` on a stated basis (`explicit_supersession`, `different_times`, `same_value`), `unresolved` after investigation, or `uninvestigated` once `maxExpansions` counterparts have been fetched in full; every pair carries the counterpart's line, and its full record when fetched. A contradiction stated only in free text is not detected, and the investigation says so. The same handle over the same store returns the same bytes. An own-scope expansion writes nothing and reads no clock; a grant-bearing one is re-checked against the clock and records its audit, as every grant read does. Once the MCP server has marked its storage unavailable (the degraded latch), `shadowgraph_expand` answers a well-formed handle `unavailable` with reason `store_unavailable` rather than failing; a grant-bearing expansion that cannot load the store before that fails closed, as every grant read does.

`traverse(input)` · `stats(options)` · `getReviewSignals(options)` carry request coverage in `completeness`. Statistics count only owned content. Signal history returns `{ items, completeness }`: another owner's signals are absent, while an own signal citing hidden facts has only identity/lifecycle fields and a limitation, with partial coverage. With no project and no origin, counts and items are empty and coverage is incomplete. `projectSummary(project)` remains a separate administrative purge preview.

`traverse(input)` is a by-id read inside the same boundary: `project` (or, with none, `originId`) decides what the root and every node reached may belong to, and a memory node must also match the requested memory scope. The walk never enters another project, legacy data or another origin, not even to come back, and a relationship stored across projects earlier is not followed. A root outside that boundary, or one that does not exist, returns the same result -- `nodes: []`, `relations: []` and `limitation: { code: 'scoped_coverage', detail }` -- which names neither the id's owner nor whether it exists. Invalid `depth`, `direction` or `scope` is refused before any id is resolved.

### Reconsideration

`review(context)` — evaluates `reopenWhen` rules against **stored** facts, so it works after a restart. It evaluates only decisions, and reads only facts, of the scope it names (`project`, or `originId`); with neither it evaluates nothing and raises no signal. Caller-supplied `facts` override stored facts of the same key; string-form rules match `changedFacts` only. `context`, `project`, `asOf`, `changedFacts`, `facts`, and nested fact values are preflight-validated before a review signal can be inserted. Returns `{ items, completeness }`; use `.items` for the due decisions. Scope coverage is distinct from evaluation, and unresolved requests report incomplete coverage.

`reconsider({ project, decisionId, changedFacts, facts, asOf })` — **a projection of the same pass**, never a second evaluation, so it can never disagree with `review()` about whether a rule fires, does not fire, or cannot be evaluated. Returns `{ verdict, evaluationCompleteness, scope, decisions }`:

- `verdict` is `review_recommended` (a rule definitely fired), `unchanged` (evaluation was complete and nothing fired), or `manual_review` (nothing definitely fired, but something could not be settled);
- `evaluationCompleteness` is `complete` or `partial`. **`unchanged` is only ever reported with `complete`.** One rule firing while another is unknown is `review_recommended` **and** `partial`, with both sets of evidence visible;
- each decision carries `triggeredRules`, `triggeredBy`, `groundedConditions` (the rules that definitely did *not* fire, so `unchanged` rests on stated evidence), `rulesNotEvaluated` (verdict `unknown` only), `contestedConditions` (decided, but on facts that disagree — these also force `partial`), `affectedAlternatives`, `factsConsidered`, and `reviewSignalId` / `reviewSignalStatus`.

Key matching is **literal**; a near-miss key is `unknown`, not a match. A stored string-form rule that `changedFacts` does not name is reported as unevaluated rather than passed. `decisionId` **fails closed**: an unknown id and an id from another project are the same error (`Decision not found`, which does not say whether the id exists elsewhere), and a closed decision is an error too -- never an empty `unchanged` result. With no project and no origin it evaluates nothing and answers `manual_review` / `partial` with `scope: { project: null, decisionId: null }` and a `limitation` (`scoped_coverage`), never `unchanged`. It raises signals under the identity `review()` already uses, so a repeat adds none, and it writes no status, confidence or lifecycle state. Contract: [review conditions](contracts/review-conditions-contract.md) §11.

`maintain(options)` preflights its object shape, `now`, `changedFacts`, `facts`, and the complete delegated review input before staling decisions, expiring facts, or appending journal entries. A rejected core or MCP maintain call leaves state, review signals, journal sequence, revision, and durable state unchanged. MCP restores the pre-call graph snapshot on any domain-operation exception before persistence. It stales, expires and reviews only what its scope owns; with no project and no origin it changes nothing and returns a `limitation`. · `acknowledgeReview(id, scope)` -- the answer shows the signal only as far as the caller may read it: a signal an earlier build raised on a fact outside the decision's boundary (it chose review evidence by project label) is acknowledged, but returned without its conditions and with a `limitation` (`scoped_coverage`); what is stored is unchanged.

### Integrity and lifecycle

| Method | Notes |
| --- | --- |
| `validate(options?)` | Returns `{ valid, issues, counts, limitation }`. `valid` is the verdict on the whole store and names nothing; `issues` and `counts` list only the scope's own issues (a journal-entry diagnostic names no project and is never listed). `valid` is false for errors and unsupported data; legacy and info diagnostics remain readable. Unknown confidence policies are preserved without v1 recalculation and reported as unsupported. |
| `repairPlan(options?)` | Plans only from the scope's own issues. Always `apply: false`. Unknown statuses route to `manual_review`, never automatic mutation. |
| `rebuild(options?)` | Replays this graph's own journal through `rebuildProjection`. Invalid baseline placement is skipped and returns `rebuildable:false` with stable issue code `invalid_projection_baseline_placement`; an incomplete fold is never presented as trusted. Whether the journal rebuilds (`rebuildable`, `reason`) is the verdict on the whole store; `projection` holds only the scope's records, facts, relations between them and their idempotency, and the entry diagnostics only its own entries, with a `limitation`. |
| `purgeProject(project, options?)` | **Logical/tombstone by default.** `{ mode: 'hard' }` physically deletes and creates a declared `seq` gap. |
| `redact(options?)` | Privacy-safe read; covers journal payloads. It redacts from the whole store but returns only what its scope owns (none with no project and no origin), and never a whole-store projection baseline. The output is a read, not a store: it carries `exportKind: 'scoped_redaction'`, set after every pattern and replacement has run, and `importData`, both stores' `save` and every restore refuse it with `public_export_not_a_store`. Redaction metadata always withholds the project label: `completeness.scope.project` is null and `projectLabelWithheld` is true for a selected project, false when unresolved. Use `requestState` to distinguish those cases; neither the metadata nor a replacement label is reusable scope authority. The actual content boundary is unchanged, ordinary read metadata retains its project label, and redaction remains `losslessItems: false`. |
| `exportData(options?)` | The public export: a read of one scope, `{ exportKind: 'public_scoped', schemaVersion, records, facts, relations, reviewSignals, events, completeness }`, with no journal, idempotency, revision or authority collections. It is not a store: `importData`, both stores' `save` and every restore refuse it with `public_export_not_a_store`. Saving, backup and restore use the internal whole-store snapshot instead. |
| `importData(data)` | Round-trip stable with the whole-store snapshot. Import preserves stored values and **never elevates trust**; legacy facts get `sourceClass` backfilled and collection-local ID remaps propagate through journal/idempotency dependencies. Direct import preflights final relation endpoints, journal type/identity/sequence/baseline placement, event IDs, review identities, idempotency namespaces, and plain-JSON values before mutation. Legacy orphaned idempotency payloads become explicit canonical entities rather than hidden cache-only state. Merge import cannot lower the live revision, journal high-water mark, or existing replay epoch. |

## 3. `validate()` diagnostics — four severities

| Severity | Meaning | Affects `valid` |
| --- | --- | --- |
| `error` | Genuinely invalid data | **Yes** |
| `legacy` | Readable, but pre-dates a contract | No |
| `unsupported` | From a newer/unknown schema or policy this build cannot interpret | **Yes** |
| `info` | Declared discontinuity, e.g. a hard-purge `journal_gap` | No |

Codes include `missing_relation_source`, `missing_relation_target`, `self_supersession`, `invalid_confidence`, `unknown_decision_status`, `unknown_verification_status`, `confidence_policy_mismatch`, `duplicate_active_fact_scope`, `duplicate_active_memory_scope`, `invalid_projection_baseline_placement` (errors) · `legacy_missing_decision_status`, `legacy_confidence_without_basis`, `legacy_fact_source_class` (legacy) · `unsupported_journal_entry`, `unsupported_journal_schema_version`, `unsupported_record_schema_version`, `unsupported_fact_schema_version`, `unsupported_confidence_policy` (unsupported) · `journal_gap` (info).

This three-way split is the answer to "don't let legacy data fail silently and don't guess-repair it": legacy data is **named as legacy**, reported, and left alone.

## 4. Storage

```js
import { createJsonFileStore, createStorage } from './src/storage.js';
import { createSqliteStore } from './src/sqlite-storage.js';
```

Both expose `load()` / `save(data)` / `close()`. State and journal are written in **one** atomic operation — `rename()` for JSON, `BEGIN IMMEDIATE`…`COMMIT` for SQLite — so they cannot diverge. Revisions are non-negative safe-integer concurrency tokens; a save or restore that cannot mint a strictly greater safe integer rejects with `revision_overflow` instead of rounding or wrapping. HTTP serializes graph mutation with persistence; MCP serializes complete tool calls including restore. HTTP and MCP reload the last durable snapshot (or the pre-mutation snapshot if storage cannot be read) after an ordinary save failure. Markdown pull accepts a persistence callback only with a paired durable read-back callback, reloads the committed snapshot so live revision/state match storage before sync-state write, and therefore resolves commit-then-throw ambiguity. JSON saves/restores and SQLite create/load/save/backup/restore operations use the same per-destination atomic `.lock` fence across handles and processes. A writer that overlaps restore waits and is checked against the installed revision, or fails explicitly; timeout is `storage_lock_timeout`, stale abandoned locks are recovered, and same-async-chain callback reentry is `storage_lock_reentrant` rather than a deadlock. SQLite opens the configured path per operation and closes it before releasing the fence, so no idle handle can pin the destination or WAL/SHM sidecars and a post-restore operation always opens the installed file. `createSqliteStore` requires a Node build with `node:sqlite` (stability 1.2, Release Candidate) and throws a clear error otherwise; tests skip on `/requires Node/`.

JSON and SQLite restore apply the shared domain validator even for direct JavaScript calls. JSON restore always runs it and a caller's `validate` only adds to it; a SQLite store built with its own `restoreValidator` uses that one in its place, but neither backend lets a caller's validator admit a scoped view (`public_export_not_a_store`), which is refused before a caller's validator runs. The same validator is used by direct import/replacement and the CLI/HTTP/MCP restore surfaces. Duplicate, ordinary midstream, rewind, wrong-epoch, and terminal-rewriting baselines reject as `invalid_projection_baseline_placement` before replacement; the narrowly compatible migration forms are defined by [ADR-0007](adr/0007-canonical-journal-baseline-placement.md). A restore copies the source's **semantic content**—records, facts, relations, review state, idempotency, events, and journal—but does not reuse the backup's concurrency token. While holding the destination fence, restore validates the source revision (a missing legacy revision means `0`), reads the current destination revision, and installs `max(destinationRevision, sourceRevision) + 1`. The source backup bytes are never rewritten. The activated in-memory graph and a fresh durable reopen expose that exact installed revision, so every payload captured before restore remains stale and raises `RevisionConflictError`; it cannot become valid again after a post-restore write. Same-path restore remains unchanged. If either high-water mark is `Number.MAX_SAFE_INTEGER`, restore rejects with `revision_overflow` before replacement.

Hard-purge `removedJournalSequences` values must be positive safe integers, unique per marker, actual replay-range gaps, and strictly earlier than their surviving marker; every gap needs a later marker, and coverage uses bounded sorted-range arithmetic rather than expanding absent sequences. SQLite additionally uses verified `VACUUM INTO` snapshots for both the source and the live rollback state, so committed WAL contents are folded into standalone files, and rejects corrupt journal folds or a records/facts/relations/idempotency projection that differs from live state. The rollback snapshot remains until the installed replacement has opened, prepared, loaded, and passed validation. Recovery inspects an existing candidate read-only before any write-capable reopen, so checking a missing destination cannot create an empty database. Caught post-replacement failures restore, reopen, and payload-compare the old state, including its exact old revision; JSON recovery restores the exact old destination bytes. An unconfirmed recovery is reported explicitly, retains its rollback artifact, and latches the HTTP server degraded so every authenticated non-health route request returns `503` until restart/manual recovery. HTTP restore is serialized with persistence and rejects concurrent mutating requests—including `/review-context`, which can generate review signals, and `/context`, which stays restore-blocked—before graph mutation. External save/restore overlap is also serialized by the destination fence. This is **process-level rollback safety**, not a claim of crash consistency or directory-`fsync` durability. Full contract: [SQLite restore](contracts/sqlite-restore-contract.md).

**Record ownership (schema 6).** Every new decision, attempt, memory and fact records whose it is: `attribution: 'project'` with its `project`, or, when no project is given but an `originId` is, `attribution: 'unattributed'` with `project: null` and that `originId` (MCP write tools accept `originId`; CLI and HTTP pass it in the JSON body). A write with neither is refused with `code: 'write_scope_unresolved'` and nothing is stored; the caller's own work is not blocked. The literal `default` is an ordinary project name. Retry keys, fact scopes and memory scopes are kept per owner, so an unattributed record never shares a bucket with a project or with another origin, and a record written before schema 6 in `default` or with no project never shares one with the real project named `default`: a new `default` write that reuses such a record's retry key gets a record of its own, and it never supersedes a legacy memory or fact. Records written before schema 6 keep their project and stay at entity schema 5 until `shadowgraph migrate [{"batchSize": n, "preservationCopy": path}]` attributes them: it writes and verifies a preservation copy of the store, then journals one `entity.attributed` entry per record in resumable batches (a rerun continues where an interrupted one stopped), mapping a stored `default` to `legacy_ambiguous` (never a real project named `default`, never inferred from content), a record stored with no project to `legacy_unattributed` (until the migration reaches it, its id is kept in the store's top-level `storedWithoutProject` list, so a save or restart in between cannot lose the distinction; earlier builds that read schema 6 carry the list unchanged), and any other project to `project`; restore validation runs before and after. `shadowgraph downgrade {"output": path, "preservationCopy": path}` writes a schema-5 copy as a separate new file, after a verified, hash-recorded preservation copy — the store, the output (with SQLite's side files), the preservation copy and the report must be four different files, checked before anything is written — and names in `<output>.report.json` everything schema 5 cannot hold (attribution fields, unattributed records, the replaced journal history, unrecognised collections); it never changes the current store. Since schema 7 every new decision, attempt, memory and fact carries an internal, random, content-free `erasureToken`, and one written earlier gets its token on its first change; no load, read, import or restore assigns one, and no public result returns one. `migrate` also backfills tokens, after attribution, in resumable batches of one `entity.token_assigned` journal entry per record, restore-validating each batch before it saves it, and reports every token the run gave under `tokens` (`backfilled` counts the backfill's own entries); a fact stored without a `kind` cannot carry a token, and a record its journal cannot replay gets one on its next change; both are listed in `tokens.skipped`. Each batch is validated against the whole store, so a large store migrates faster with a larger `batchSize`. `downgrade` takes `toSchemaVersion`, `6` or `5` (the default): `6` writes a schema-6 copy without the claim-evidence fields and tokens, names every removed field per record, leaves out and names an attempt captured with no result class (a schema-6 reader would classify it from its prose), and carries every other collection, access grants included, as a backup does, except the runtime miss ledger and capture's `captureContent` and `captureSessions`, which it leaves out and counts in `excludedEntryCounts`; it also leaves out and names every capture item; `5` goes through 6 and gives one report.

**Claims (schema 7).** A decision, attempt, memory or fact may carry `claims`. The local claim verifier (`claim-verifier-v1`: deterministic, no model call, English lexicons) classifies a claim against the source it cites and fails safe. A claim is `quoted` only where it occurs verbatim (folding whitespace and letter case) and the source says nothing else: the claim's own sentence or line holds nothing beside it but a list bullet or number, "the", "a", "an" and closing punctuation, and every other line or sentence of the source that does not itself hold the claim uses only structural heading words ("Summary:", "Output", "Notes"), with no question and no markup. A deterministic reader cannot tell which other sentence retracts, hedges or narrows a claim, so a source that says two things vouches for neither: most multi-sentence sources yield no quoted claim, by design (fidelity before yield). `entailed` is the same after a named rule (recorded as `rule`); `ambiguous` is the claim said plainly in one place and narrowed by quantity, actor, time or scope in another, and nothing else (the `readings`, and the plain place as `span`); anything else is `unsupported`, with the dimension that failed. `verifiedClaims` returns quoted, entailed and ambiguous claims as accepted and unsupported ones apart, counted by dimension. Import and restore refuse a stored claim that is `unsupported`, names no `verifierVersion`, or lacks what its class needs (its text and `sourceRef`; a `rule` if `entailed`; `readings` if `ambiguous`; a well-formed `span` if it has one). They check presence and shape, not which verifier ran, so a later verifier's claims stay readable; an entity of a future schema is carried verbatim, unchecked. A `causalClaim` with a class must name its `verifierVersion` too. No write path takes a caller's claims: they are dropped, or the request is refused. A claim class never sets `verificationStatus`.

**Attempt causes (schema 7).** Every attempt carries a `causalClaim`, the cause attributed apart from the observation it explains, so an attempt's `sourceClass` never vouches for its `reason`. `recorded`: the caller gave a reason; the claim is `agent_claimed` whatever the attempt's own `sourceClass`, with no evidence, and its statement is `reason` itself. `not_recorded`: no reason, or only whitespace. `unknown`: the cause is recorded as unknown (only an extractor writes it). `legacy_freetext`: an attempt stored before causes were, whose reason is kept but never classed or evidenced. That state is shown, not stored: such an attempt is kept exactly as the earlier build wrote it, so a store this build writes to stays restorable by that build. Journal entries, retry values and a caller's own values are shown as written. `reason` is unchanged: stored and returned verbatim and searchable as before. A caller cannot set `causalClaim`; it is derived from `reason`. Downgrading to schema 6 removes `causalClaim` and lists it in the report; importing that copy again gives an attempt with a reason `legacy_freetext`.

The runtime miss ledger (`runtimeMisses`) is a top-level collection of operational data whose entry shape this build freezes and validates at import and restore (`runtime_miss_ledger_malformed`); no public read returns it, a project's purge removes and counts, in both modes, the entries recorded in the project or naming an entity it removes, and conversion to schema 6 or 5 leaves it out, reporting only `excludedEntryCounts` (plan rev6 PR-28a). A `context()` read with query text that the fallback answers records a record it delivered as a runtime miss -- one per read, each record once per query, scope and record, none over 1 KB, at most 100 kept, with a SHA-256 digest of the query and never its text; none for a query naming a stored entity's id -- and saves nothing itself: the process's next save, whatever operation makes it, writes it, and a granted read writes it in the save it already makes (PR-28). The store reads capture before anything writes it (plan v1.4.4 §9.5, PR-33): a capture item is a `records[]` entry of kind `capture` at schema 7 or later, which a build before this one refuses. Import and restore check its frozen shape -- `id`, `kind`, `schemaVersion`, `project`, `attribution` (`project` or `unattributed`, never legacy), `originId`, `state` (`pending`, `processing`, `extracted`, `failed` or `blocked`), `source` (`event`, `sessionId`), `observedAt`, `occurrenceSeq`, `sourceIdentity`, `contentRef`, `contentHash`, `lease` (null, or naming its `leaseId`, `ownerId`, `ownerBootId` and `leaseExpiresAt`), `attempts`, `lastError`, `blockedReason`, `producedRecordIds`, `receipts`, `erasureToken`, `cancelRequested`, `supersededResults` (the plan's `superseded_result` records), `possibleDuplicateOf`, `expiresAt`, `createdAt`, `updatedAt`, and no `generation`; a failed item says why in `lastError`, a blocked one in `blockedReason`; any other field is carried -- and name the item's position; one of a future schema is carried verbatim and blocks restore. Only a store that declares its `schemaVersion` carries a capture item; a legacy store's migrations never rename one, and no relation may name one at any schema. A merge import joins capture's collections by key, never dropping another capture's entries and never moving one to another owner. Capture's `captureContent` (keyed by `contentRef`) and `captureSessions` (keyed by `id`, one per origin session) collections are arrays of entries that name their owner; a malformed one is refused with `capture_collection_malformed`. No public read gives any of it meaning: no public read, export, redaction, journal page, validation listing or rebuild shows a capture item, entry, token or text, and a capture id is an unknown id to every by-id read and write. A privileged writer (PR-34) records capture items and moves them along the plan's §12.5 edges; nothing in the product calls it yet. It keeps each session's count in its `captureSessions` entry as `occurrenceSeqHighWater`, and takes each item's `occurrenceSeq` past both that mark and every ordinal a live capture of the session holds. ShadowGraph's own traffic (a call to its MCP server; a run of its binary or of its installed runtime's entry points; a touch of its store and its side files, activation record or marker files; a correlation token it minted; its worker's sessions) is counted there as `selfEvents` -- declared operational metadata, by signal (`S-1`, `S-2`, `S-3`) and event, carried as it is at import and restore (a merge of an earlier copy replaces them with that copy's) -- and never recorded; a session a self-event opens takes the owner of its first capture. A delivered ShadowGraph block whose closing line counts its bytes is removed from captured text before it is stored. Counts of removal do include capture material: a purge counts the items it removes in `removed` and their entries in `journal` (the preview's `journal` too), a hard purge declares their sequence numbers, and a restore's `records` counts them. Attribution refuses, with `attribution_capture_unsupported`, an origin that holds a capture item and a record a capture names anywhere (as one it produced, in a receipt or in a superseded result); nothing on this build attributes capture. A top-level collection this build does not recognise is carried through load, save and restore unchanged in both backends (JSON keeps the key; SQLite keeps it in the generic `shadowgraph_extra` table), and is never part of `exportData()`, `GET /records`, `list` or redaction output. Restore preserves or narrows destination authority under the PR12 authority rules; it never widens it from the backup. `shadowgraph restore <path> --memory-only`, `memoryOnly: true` on HTTP `/restore` or MCP `shadowgraph_restore`, and the library restore options exclude `access` and `accessRevocations` while restoring memory. Mandatory restore validation and recovery diagnostics still apply. SQLite carries extension collections in `shadowgraph_extra`; no new storage format is introduced.

JSON restore inventories `.rollback`, `.recovery`, and `.tmp` paths without replacing the primary restore outcome when `stat` itself fails. `json_restore_recovery_unconfirmed` always remains the error code; `retainedArtifacts` lists files confirmed present, while `unknownArtifacts` contains `{ path, code }` entries whose existence could not be determined. HTTP and MCP latch every graph read/write closed before accepting a later operation; authenticated HTTP health and MCP error diagnostics carry the same inventory. The intentionally public static dashboard never includes recovery diagnostics.

After a successful JSON restore or a confirmed rollback, cleanup attempts and then inspects every artifact path. An anomalous cleanup result/error includes `retainedArtifacts`, `unknownArtifacts`, and `artifactCleanup: { status, errors }`, where `status` is `complete`, `incomplete`, or `unknown` and each cleanup error is `{ path, code }`. Final inspection is authoritative: a delete-that-then-throws is reported as `status: "complete"` with an empty `retainedArtifacts`, never as a retained file. Ordinary clean success keeps the existing `{ source, destination, records }` result shape.

### U-1 — Verification channel

**Status: implemented in schema 5.** Ordinary fact writes still cannot create `verificationStatus: 'verified'`. A graph/server may be constructed with a separate local verifier whose trust store is not caller input. `verifyFact({factId,evidencePath,project,originId})` accepts only those fields, verifies only a fact its write scope owns (another project's fact and a missing one are both `Fact not found`), and verifies a closed-shape Ed25519 attestation inside a configured evidence root. The signed digest binds the canonical fact claim, verifier identity, evidence reference, method, and verification timestamp. Invalid/tampered evidence rejects before fact, event, or journal mutation. Signed verification survives export/import, journal rebuild, and JSON/SQLite restart; expired facts cannot be promoted back to effective verification during import.

MCP exposes `shadowgraph_verify_fact` only in full mode when `SHADOWGRAPH_VERIFIER_CONFIG` is set. The caller never supplies the trust key, verifier identity, signature, method, or target status through tool arguments.

### U-2 — Privileged tool re-verification

**Status: deferred.** Tool-observed claims are stored and weighted only as declared policy inputs; they never verify a fact.

### U-3 — Legacy verified values

**Status: implemented migration.** A schema-1–4 unsigned `verified` value becomes effective `unverified` with `legacyVerificationStatus: 'verified'`. It remains visible for audit but is never trusted as a signed attestation.

### L-1 — Entry state

**Status: implemented.** New decisions enter `proposed`. Current/actionable context is defined by the explicit current-state set rather than a literal `active` value. Schema-4 `active` migrates to `proposed` with `migration.legacyDecisionStatus`.

### L-2 — Transition enforcement

**Status: implemented.** `DECISION_TRANSITIONS` defines every legal caller transition. `stale` and `superseded` are system-owned. Illegal transitions reject before decision/event/journal mutation.

### L-5 — `stale` / `archived`

**Status: implemented.** `maintain()` produces `stale` when a current decision reaches `reviewAfter`; callers cannot self-assign it. `archived` is an explicit terminal disposition, distinct from `abandoned`, and excluded from current context and automatic review.

### Review-signal acknowledgment audit scope

**Status: accepted provisional.** Acknowledgment is persisted in the projection/storage snapshot but is not journalled or replayed. Rebuild therefore reconstructs domain records/facts/relations/confidence/idempotency, not review-signal acknowledgment history. Actor/session audit for acknowledgment is deferred; the product currently requires review signals, not an immutable acknowledgment audit trail.

### Host delivery

`shadowgraph deliver` serves two hook events. It reads the event from stdin (`hook_event_name`, and `prompt` for `UserPromptSubmit`) -- one JSON object, read until it parses, for at most a few seconds and 1 MiB -- and writes at most one line, `{"hookSpecificOutput":{"hookEventName":...,"additionalContext":...}}`, for the host to add to the model's context. It is strictly a read: the store (`SHADOWGRAPH_FILE`, `SHADOWGRAPH_STORAGE`) is read as it is, at any schema version, and nothing is saved, stamped, locked, created or migrated -- a missing store is not created, and a SQLite store is opened immutable and read-only. It always exits 0, writes nothing to stderr, and emits no field that could block or steer the host.

`additionalContext` is plain text of at most 8 000 bytes, in this order: a constant line framing what follows as data, not instructions; `head:` (the trigger, whether the store was available, the scope and request state, completeness, the limitation, whether relevance was established or not assessed, what the read found -- `total`, `hasMore`, `limitSource`, `byKind` and its temporal counts -- and how many records were delivered, omitted, left out to fit, withheld, or `notExamined` -- past the first 200 the payload looks at); `processing:` (capture and extraction are not active); one `item:` per delivered record, in the order described below -- a claim line with its expansion handle (T1), or the full record (T2), each with its event-time state and current state; `expansion:` (how to reach what was not delivered); and a closing `end: shadowgraph-deliver <n> bytes`, the byte count of everything before it. Each line is JSON with line and paragraph separators, C1 and bidirectional controls escaped, so no delivered text can begin a line of its own. Records are taken in order while they fit; one that does not is left out whole and counted. If the head alone would exceed the cap, or would itself still hold something the credential check flags, a reduced payload is sent instead: the frame, a head with only the counts and `limitation.code` `head_too_large` or `head_withheld`, the processing block and the byte count. Credential-shaped values are redacted before anything reaches stdout -- from the record values themselves, read as stored and again in a folded form (compatibility characters folded, invisible format characters removed) that shows a disguised name, before a claim line is rendered from them; text in which nothing is found keeps its original characters: known token shapes, private key blocks (across fields too, a body cut short included), credentials in URLs and command-line flags, credential-named values in text and in config syntax (name and value both), credential-named fields, the values under credential-named keys, and record keys themselves; an object or array nested more than 100 levels deep is replaced whole. Text that redaction cannot clear, as stored or folded, is left as stored. The package checker's own credential detector then runs on every value and key, as stored and folded, on every line and on the escaped payload, and an item it still flags is withheld and counted, so nothing that detector recognises reaches stdout. Recognition is pattern-based, so a credential of a shape neither layer knows can still be delivered. The 8 000-byte cap is a conservative tested-complete bound, not a host guarantee.

At `SessionStart` there is no prompt, so relevance is not assessed and the working set follows -- the read's declared fallback, as full records (T2), newest first and mixed by kind among its first 1 000 records (current decisions, failed and reusable attempts, then stale facts), as far as the cap allows. At `UserPromptSubmit` the records come in the read's relevance order. The session start also says what state memory is in: a store that is missing, unreadable, busy (a SQLite store another ShadowGraph process has open: its write-ahead or rollback journal or its fence present, or the file changed while it was read) or written by a newer build is reported `unavailable` in a reduced payload (the frame, a head with the reason, the processing block and the byte count), and a workspace with no project resolved is reported as such -- never as an empty, complete answer. At `UserPromptSubmit` the prompt is ranked against the store and only relevant records are delivered; otherwise nothing is -- neither an irrelevant history nor a repeat of a state the session start already gave. The project comes from the workspace binding, as on every read that names none.

With `--hook` the command is inert -- it reads no input, opens no store and prints nothing -- unless the per-user activation record `activation.json`, under `SHADOWGRAPH_HOME` or else `~/.shadowgraph`, is a regular file whose `capabilities.delivery.state` is `active` and which pins a store by absolute path. A relative `SHADOWGRAPH_HOME` is never trusted. When it is active the hook reads that pinned store only -- never `SHADOWGRAPH_FILE` or a `.shadowgraph/data.json` a working tree holds -- and only a worktree binding selects a project, when the pinned store has recorded the same binding (`shadowgraph bind`), so a cloned repository's files choose nothing; a shared-repository binding is not honoured there, since a `.git` file placed in any directory can name another repository, and nothing is selected in a directory git places outside the work tree it names (a shipped `.git` can set `core.worktree` to the owner's). Memory recorded in any other store is not delivered: see the Claude Code section of `integrations/README.md` for pointing the MCP server and `bind` at the pinned store. On Windows the CLI never looks for a program in the working directory, so a `git.exe` a workspace holds is never run. The head then carries `host`: the Claude Code version recorded at activation, the version the delivery evidence was verified on (`integrations/claude-code.coverage.json`), and whether they match; another version is delivered as unverified. The work -- with or without `--hook` -- runs in a worker thread while the main thread keeps a deadline of 5 000 ms, below the hook's 10-second timeout: past it the command exits 0 having printed nothing, however far the work had got. The deadline was frozen from measurement, at more than six times the largest p95 measured (788 ms at 6 688 records, 10 runs). `SHADOWGRAPH_DELIVERY_DEADLINE_MS` can only shorten the deadline. No lock is waited for: a JSON store is read without one, and a SQLite store another process holds is reported busy at once. A delivery skipped for time or an unavailable store is not reconstructed later; the next one reads the store as it then is.

`shadowgraph install-hooks` adds the hook block of `integrations/claude-code.hooks.json` -- a command handler running `shadowgraph deliver --hook` with a timeout, at `SessionStart` and `UserPromptSubmit` only -- to one Claude Code settings file: `~/.claude/settings.json`, or the file `--settings` names. Every earlier ShadowGraph handler (any command handler running ShadowGraph's `deliver --hook`) is removed first, so exactly one generation is registered; every other setting and hook is kept. `shadowgraph uninstall-hooks` removes ShadowGraph's handlers and nothing else, along with any group, event list or `hooks` key that only they filled, so an install followed by an uninstall gives back the same settings in effect (a `hooks` map or event list that was empty before the install is not kept). The path is first resolved to the file it reaches -- through a short (8.3) name, a junction or a link -- and that file is the one checked and changed, so a link stays a link. Nothing is written when nothing would change, the current generation already being in place (an absent file stays absent). Otherwise the owner is asked to type `confirm` at a terminal -- for every file except a scratch file under the system's temporary directory that is in no `.claude` or `.shadowgraph` directory and has no name Claude Code reads (`.claude.json`, `settings.json`, `settings.<scope>.json`, `managed-settings.json`, `hooks.json`); nothing is a scratch file when that temporary directory holds the user's own home -- and without a terminal the command fails and writes nothing; the file must still hold what was read when the owner answered, or nothing is written. This guards host settings against an accidental change; it does not stop a process that can already write the file. The file is replaced through a temporary file and a rename; a failed write leaves no temporary copy. A file that is not a JSON object, or whose `hooks` is not a map of lists, is refused unchanged; other JSON is written back with two-space indentation. Each prints `{ settings, changed, events, note }` or `{ settings, changed, removed }`, `settings` being the resolved path. Installed hooks stay silent until delivery is activated. Remove the hooks before uninstalling ShadowGraph, since each hook otherwise runs a command that no longer exists. `--runtime <directory>` installs a handler that runs a pinned runtime instead of the `shadowgraph` on the path: that Node binary and the runtime's own CLI. A path either shell would expand (a quote, `$`, a backquote, `%`, `!`) is refused. The handler names that Node binary's path and the runtime's directory: if either is removed -- Node upgraded or moved, the runtime deleted -- every hook fails at once, before it can read the activation record, so `deactivate` does not silence it; run `uninstall-hooks` (or install them again for the new path) before removing either.

`shadowgraph activate delivery --evidence <ref> --store <path> [--storage json|sqlite] [--host-version <version>] [--settings <path>] [--runtime <directory>]` writes the activation record: the evidence reference of the gate that allows it, the store the hook reads (which must exist), the host version (read with a bounded `claude --version` when not given, `unknown` when that fails), the deadline, the payload cap, the hook timeout, the settings file and whether ShadowGraph's hooks are installed in it, the pinned runtime when named, and the acting surface, with the history of every change, each activation's store and runtime included. The store must be readable as the kind declared (a store another process holds counts as readable), and the output warns when it lies in a git working tree, since what that repository ships could change it. The evidence reference is refused when the credential check flags it, and the host version must be `x.y.z` or `unknown`. It needs the owner to type `confirm` at a terminal unless the record is a scratch file (the temporary directory is the one the environment names, so whoever sets it and `SHADOWGRAPH_HOME` together decides what is scratch: the confirmation guards against an accident, not against the environment's owner), and nothing is written if the record changed while the owner decided. `shadowgraph deactivate delivery` turns delivery off and never asks; the history keeps both entries. It always leaves a record saying delivery is off: a record whose content is unreadable is renamed aside, never deleted, and named in the output; one the system cannot read for now, another process holding it, fails the command and is left as it is. Run it with the `SHADOWGRAPH_HOME` Claude Code's hooks see, and check the `file` it prints. To turn delivery off, deactivate first, then uninstall the hooks. The record holds configuration and references, never memory. A host that updates after activation stays recorded at the version activation saw, until the next activation: the version is checked there and nowhere else.

`shadowgraph activate capture --evidence <ref> --store <path> [--storage json|sqlite] [--only <project,...> | --exclude <project,...>] [--host-version <version>] [--settings <path>] [--runtime <directory>]` is the owner's one explicit enablement of automatic capture, recorded as `capabilities.capture` in the same activation record. Capture then covers every project unless `--exclude` leaves some out or `--only` names the ones it covers; it never changes what any read returns. The store must exist, read as the kind declared, and lie outside every git repository and working tree: a store below a directory holding `.git`, inside a `.git` directory or inside a bare repository is refused (`capture_store_inside_repository`), with its path followed through links, the invoking environment's `GIT_DIR` or `GIT_WORK_TREE` asked too, and a git that cannot rule a repository out counted as one; no flag, variable or key permits it, and an existing manual store inside a working tree keeps working by hand. A working tree whose git directory lies elsewhere (`core.worktree`, as some dotfiles set-ups use) leaves no trace on the store's path and is not detected. Delivery and capture work on one private store: while both are active they must name the same store and the same pinned runtime, so a re-pin turns capture off, re-activates delivery on the new runtime and then activates capture on it again. No host version is recorded as verified for capture until its gate records one. The record keeps an origin minted at the first activation and reused by every later one, the coverage, and the frozen admission limits (`maxStoreBytes`, `maxQueueDepth`, `maxItemBytes`, `maxItemsPerSession`); the history keeps each activation's store, coverage and limits. As for delivery, the owner types `confirm` at a terminal unless the record is a scratch file. `shadowgraph deactivate capture` turns capture off and never asks. Nothing in this build captures yet: the hook that reads this record arrives later, and capture stays off until it is approved on the real host.

`node scripts/install-runtime.mjs [--commit <revision>] [--home <directory>]` installs a pinned runtime: the commit's build exactly as `npm pack` makes it, under `<SHADOWGRAPH_HOME or ~/.shadowgraph>/runtime/<commit>/`, with the tarball kept beside it and `runtime.json` naming the commit, its tree and the tarball's SHA-256. Whenever the runtime is named it is checked again: the tarball against its digest, and every file the hook runs against the tarball, byte for byte, none missing and none added. It is installed once per commit, only under a path that names ShadowGraph, and after the owner confirms at a terminal unless the path is a scratch location.

`node scripts/context-size.mjs --deliver [--runs N] [--records N]` measures the hook's latency: `deliver --hook` at each event over a seeded store, against a matched no-op process spawned the same way, as p50, p95 and maximum wall-clock milliseconds. On the development machine, with a 50 ms no-op, the hook took a p95 of about 300 ms at 176 records, 500 ms at 1 760 and 790 ms at 6 688 records. A host's own latency is measured at the activation gate.

### SQLite carrier diagnostics

`createSqliteStore(...).validate()` inspects reserved native/control collection
names in `shadowgraph_extra` under the destination fence with a read-only
handle. It returns `{ valid, issues }`, where each issue has code
`sqlite_extra_reserved_key` and the reserved `collection` name. It reads no
carrier payload and changes no data. Load still ignores these conflicting rows;
the existing save path removes them. Unknown collections remain preserved.

Local `shadowgraph doctor` includes `storage.diagnostics` and exits 1 when this
check finds a collision. Clean doctor output is unchanged. These store-wide
administrative diagnostics are not attached to scoped HTTP/MCP graph reads.
